CS SmartHub

업무 자동화 · 풀스택 · 사내 도구

소스 보기핵심 발췌본 · 실사용 모듈 5개 포함, 회사·고객 정보는 제거
문제CS 4인 팀이 매일 메일 발송 확인과 아침 로그 점검을 손으로 반복했고, 도구가 낱개 스크립트라 팀이 늘면 복사해서 고쳐 써야 했습니다.
인사이트
  • 팀이 달라도 일의 모양은 같다 — 팀(허브)과 기능(모듈)을 분리하면 늘어도 복사하지 않습니다
  • 내가 매일 쓸 도구라야 끝까지 다듬어집니다
해결방안
  • 허브×모듈 구조: 모듈 하나를 등록하면 백오피스 토글·요약·보안 표에 자동 반영

  • 허브별 비밀번호와 모듈 보안 레벨로 공개 허브의 위험 모듈을 차단
  • 사내 배포 자동화: 서버에 이미지를 직접 올리던 방식을 deploy 브랜치 머지만으로 끝나게 바꿨습니다. CI 서버가 사내망에 들어올 수 없다는 걸 시험 파이프라인으로 먼저 확인하고, 밀어 넣는(push) 설계를 사내 클러스터가 2분마다 새 이미지를 확인해 가져가는(pull) 방식으로 뒤집었습니다. 배포 권한은 서비스 하나로 한정해 공용 클러스터의 다른 서비스에 닿지 않게 했습니다

LLM 위키 (sj-wiki)

개인 비서 · LLM 메모리 · 운영 규칙

LLM의 기억을 모델이 아니라 저장소에 둡니다. 어떤 기기·에이전트로 열어도 같은 규칙과 같은 맥락으로 일하는 나만의 비서입니다.

Karpathy의 LLM Wiki 아이디어를 바탕으로 운영 규칙(스키마)부터 직접 설계하고, 오픈소스를 확인하며 지속적으로 고도화 중

소스 보기위키 본문·운영 규칙·수집 도구 포함 · 공개 저장소
문제LLM은 기기·세션·도구가 바뀌면 나를 처음부터 다시 설명해야 하고, 같은 질문에도 답의 관점과 수준이 달라집니다. 대화 기억이나 기기 안의 메모에 기대면 다른 환경에서는 이어지지 않습니다.
인사이트
  • 일관성은 모델의 기억이 아니라 모델이 읽는 문서에서 나옵니다 — 기억을 저장소에 두면 어떤 환경에서도 같은 상태로 시작합니다
  • LLM에게 쓰기를 맡길수록, 무엇을 읽기 전용으로 두고 무엇을 점검할지 규칙이 중요합니다
해결방안
  • 운영 규칙을 저장소에 둠: 같은 스키마를 Claude Code용(CLAUDE.md)과 Codex용(AGENTS.md)으로 두어 어느 에이전트든 같은 방식으로 일함
  • 내 프로필 페이지를 모든 답변의 관점 기준으로 지정, 모든 페이지 맨 앞에 내 관점의 핵심 요약을 강제
  • Git 동기화와 새 기기 시작 절차(pull → 작업 → push)를 문서화 — 기기에 종속된 개인 메모에 의존하지 않음
  • 원본(raw)은 읽기 전용, 위키는 LLM이 작성·유지하고 변경 이력은 append-only 로그로 기록
  • 건강검진 점검: 끊긴 링크·고아 페이지·오래된 정보·모순을 코드로 찾아 주 1회 리포트
  • 회사 기밀은 공개 저장소에 두지 않는 분리 원칙과 .gitignore 안전망
  • 오픈소스를 확인해 계속 개선: LLM Wiki 아이디어로 시작해, 그래프 가시성은 Obsidian 오픈소스 플러그인으로 보강하고 도입을 검토한 도구는 위키 페이지로 정리해 쓸만한 것만 반영
  • 반복적이고 양이 많은 데이터(AI 뉴스·게임 요소)는 위키에서 떼어 RAG 검색으로 연결 — 다음 프로젝트

위키 RAG 검색

RAG · 검색 API · 평가

LLM 위키에서 반복적이고 양이 많은 데이터만 골라 검색 가능한 RAG 데이터로 만들고, 다른 프로젝트가 호출할 수 있는 API(키 필수)로 열었습니다.

검색 체험실제 API로 검색 · 답변은 실시간 스트리밍 · API 장애 시 정적 BM25로 대체
소스 보기API 소스와 평가 질문셋
문제위키에 AI 뉴스(주간 정리)와 게임 요소 라이브러리처럼 같은 형식이 반복되고 분량이 큰 데이터가 쌓였습니다. 이를 매번 통째로 LLM에 읽히거나 사람이 직접 찾기에는 비효율적입니다.
인사이트
  • 정리된 맥락은 위키(LLM의 메모리)에 두고, 분량이 큰 반복 데이터만 검색으로 분리하면 둘이 서로 방해하지 않습니다
  • 검색은 만들고 끝이 아니라 질문셋으로 재서 고쳐야 합니다 — 직접 재 보니 BM25는 단어가 같은 한국어 질의에는 거의 완벽했지만, 영어·동의어 질의에서는 hit@5 0.20에 그쳤습니다. 의미 검색(임베딩)이 필요한 구간을 감이 아니라 수치로 확인했습니다
  • 도구를 더 붙이기 전에 근거부터 따집니다 — RRF로 두 검색 결과를 합칠 때 한쪽에만 걸린 청크가 불리해지는 약점을 분석했고, 무료 쿼터와 규모를 고려해 리랭커는 보류했습니다. 평가셋 보강 → 융합 설정 비교 순서로 진행합니다
해결방안
  • 대상 선별: 위키 107페이지(게임 85·AI뉴스 22)를 헤딩 기준으로 3,808개 청크로 분할
  • BM25(한글 bigram) 검색 + 벡터 유사도를 RRF로 합치는 하이브리드 구조로 구현 — 임베딩 모델을 연결하면 켜지고, 현재 배포본은 임베딩 연결 전이라 BM25 기반으로 동작
  • 검색·답변·상태 확인 API(search·ask·health)를 열어 다른 프로젝트에서 참조 — 모든 엔드포인트가 API 키 필수(키가 없으면 거부하는 fail-closed)
  • 답변은 LG의 무료 K-EXAONE 2.5(OpenAI 호환 API)로 생성하고 스트리밍으로 글자가 나오는 대로 표시 — 근거를 4개·600자로 줄이고 대기 중에는 진행 표시를 보여 체감 속도를 개선
