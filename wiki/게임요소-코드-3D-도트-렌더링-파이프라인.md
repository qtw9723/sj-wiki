> [!tip] 핵심 takeaway
> 🧠 "도트 게임 = 도트를 하나하나 찍는 것"이 아니라, **3D 장면을 작게 그려 크게 늘리고(5개 스위치) 도트처럼 후처리**하는 길도 있다. Unity 경험([[내-프로필]])을 살려 도트 인디 게임을 만들 때, 캐릭터 애니메이션을 3D 리깅으로 해결하는 대안 경로로 검토할 만하다.
> 📄 핵심은 순서대로 켜는 5개 스위치: ①저해상도+최근접 확대 ②조명 3단계 ③깊이 기반 외곽선 ④32색 팔레트+베이어 디더 ⑤초당 12포즈.
> ⚠ 이 페이지는 영상의 **설명란·챕터 기준**이다(자막 수집 실패, [[게임요소-라이브러리]] §7 `수집` 단계).

## 핵심 규칙
📄 아래는 영상 설명란에 적힌 파라미터이며, 한 장면에 **스위치를 하나씩 켜는** 방식으로 설명된다.

| # | 스위치 | 하는 일 | 📄 설명란 파라미터 |
|---|---|---|---|
| 1 | 해상도 낮추기 | 3D 장면을 작은 렌더 타깃에 그린 뒤 화면에서 정수배로 확대 | 320×180 렌더 타깃, **최근접(nearest) 필터** ×4 |
| 2 | 계단 조명 | 부드러운 음영을 몇 단계로 끊는 툰 셰이딩 | 밝음·중간·어둠 **3단계**, 그림자 맵도 부드럽게 섞지 않음 |
| 3 | 외곽선 | 깊이 버퍼의 이웃 값 비교로 선을 그림 | 상하좌우 1칸과 비교 → **내가 더 가까운 칸에만 1px** 선, 면 방향이 크게 꺾이는 칸은 살짝 밝게 |
| 4 | 색 줄이기·망점 | 모든 픽셀을 정해 둔 팔레트 색으로 치환, 사전에 디더 가산 | **32색 팔레트**, 최근접 색은 **OKLab 거리**, 치환 전 **4×4 베이어 디더**를 약하게 더함 |
| 5 | 동작 끊기 | 위치는 매끄럽게, 포즈만 낮은 프레임률로 갱신 | 위치는 매 프레임, 애니메이션 자세는 **초당 12회** |

📄 ×4 확대 기준 320×180 → 1280×720 (🧠 단순 곱셈).

### 의사코드 (🧠 설명란 지시문을 풀어 쓴 것 · 미구현·미테스트)
```text
// 엔진 무관 의사코드 · 테스트 안 함
scene_rt  = render(scene, size=320x180)            // 스위치1 + 스위치2(조명 3단계로 양자화)
for each pixel p in scene_rt:
    // 스위치3: 외곽선
    if depth[p] < min(depth[up], depth[down], depth[left], depth[right]) - eps:
        color[p] = OUTLINE_COLOR                   // 내가 더 가까울 때만 1px
    else if normal_change(p, neighbors) > THRESH:
        color[p] = brighten(color[p], small)       // 꺾이는 면의 능선
    // 스위치4: 팔레트 + 디더 (맨 마지막 패스)
    c = color[p] + bayer4x4[p.x % 4][p.y % 4] * WEAK
    color[p] = nearest(PALETTE_32, c, metric=OKLab)
present(scene_rt, scale=4, filter=NEAREST)
// 스위치5: 애니메이션은 시간을 1/12초 단위로 내림해서 샘플
pose_time = floor(t * 12) / 12 ; position = continuous(t)
```

## 실패 사례와 해결 (📄 챕터 3:41, 설명란 지시문)
- 📄 해상도를 낮추자 **주인공 눈이 사라졌다**. 원인은 눈이 **1칸(픽셀)보다 작아졌기 때문**이라는 취지로 지시문에 반영돼 있다.
- 📄 해결: **해상도를 올리거나, 머리를 키운다.**
- 🧠 일반화: 저해상도 파이프라인에서는 "보여야 하는 최소 디테일(눈·손·아이템)이 몇 픽셀인가"를 먼저 정하고 해상도·비율을 거기에 맞춘다.

## 왜 재밌나
- 🧠 **감각**: 도트 특유의 레트로 질감을 유지하면서 3D의 조명·회전·카메라 연출을 얻는다.
- 🧠 **표현**: 팔레트·조명 단계·외곽선 색을 바꾸는 것만으로 화풍이 크게 달라져 아트 방향을 빠르게 실험할 수 있다.

## 출처 게임별 변형
- 📄 [[게임요소-사례-데드-셀]] — 영상이 "같은 방법을 쓴 게임"으로 제시(Thomas Vasseur, Game Developer 2018 글을 사례 출처로 인용). 구체적 구현 차이는 이 페이지에서 확인되지 않음.

## 조합 궁합
- 🧠 잘 맞음: 2D 스프라이트처럼 보여야 하는 **액션·플랫포머**(캐릭터 애니메이션을 3D로 재사용). 
- 🧠 충돌 가능: 극단적으로 작은 해상도에서 얼굴 표정·작은 UI 글자 표현(위 눈 사라짐 사례와 같은 문제).

## 구현 메모
- 난이도 3 🧠(풀스크린 후처리 패스 + 팔레트 변환 필요).
- 🧠 Unity에서는 낮은 해상도의 렌더 텍스처에 그리고 필터 모드를 Point로 확대하는 방식이 기본 골격이다(URP의 풀스크린 패스/Renderer Feature로 3~4번을 얹는 구성 — 이 위키에서 미검증).
- 🧠 조정 손잡이:
  | 손잡이 | 올리면 | 내리면 |
  |---|---|---|
  | 렌더 해상도(320×180) | 디테일 보존, 도트 느낌 약화 | 도트 느낌 강화, 눈·손 등 소실 위험 |
  | 조명 단계 수(3) | 입체감 증가 | 그래픽한 느낌 |
  | 팔레트 색 수(32) | 색 표현 풍부 | 통일감 강화, 밴딩 증가 |
  | 디더 강도 | 그라데이션 표현 | 깔끔한 면 |
  | 포즈 갱신(12/s) | 부드러움 | 손그림 애니 느낌 |
- 📄 시리즈 취지상 위 지시문은 **AI(코딩 에이전트)에 그대로 전달**하는 용도로 쓰였다. 🧠 Claude Code에 같은 지시를 줄 때도 수치(320×180, 32색, 12/s)를 첫 시도의 기준값으로 쓰면 된다.

## 인터페이스
- 입력: 3D 씬(캐릭터·조명·그림자), 팔레트 32색, 렌더 해상도, 확대 배율.
- 출력: 최근접 확대된 도트풍 화면. 
- 상태: 없음(프레임 단위 후처리). 애니메이션만 시간 샘플링 규칙(1/12초)을 가진다.

## 코드
- 📄 설명란에는 코드가 아니라 **AI용 지시문**만 있다. 위 의사코드는 🧠 이 지시문을 풀어 쓴 것이다. 실행 가능한 코드는 직접 구현 후 `gl_repo`로 연결할 것([[게임요소-라이브러리]] §6).

## 테스트 방법 (🧠 제안)
1. 스위치 1~5를 영상처럼 **하나씩 켜며** 스크린샷을 비교한다(`raw/assets/`, 직접 찍은 것만).
2. 캐릭터의 눈·손이 1픽셀 이상으로 보이는지 확인한다.
3. 정지 화면에서 팔레트 32색 이외의 색이 없는지 확인한다.
4. 이동 중 외곽선이 깜빡이지 않는지 확인한다.
통과하면 `gl_status`를 `검증`으로 올린다.

## 의외의 연결점 (🧠 판단)
- **눈이 사라짐 = 표시 해상도보다 작은 신호.** 같은 날(2026-11-04) [[게임-크롤러-스팀-크리틱]] §7 12일차에서 Valheim의 하루 평판 하락(증분 부정 23.8% vs 누적 6.4%)이 Wilson 0.1%p 표시에서 보이지 않았다. 영상의 해결책 두 개(*해상도 올리기* / *머리 키우기*)가 크롤러 쪽 *증분 비율 따로 표시* / *며칠치 합산* 과 같다. 저해상도 파이프라인의 "최소 디테일 몇 칸?" 질문은 데이터 대시보드에도 그대로 통한다.
- **스위치 5(위치 매 프레임 · 포즈 12/s) = 채널별 갱신 주기.** 바뀌는 값과 거의 안 바뀌는 값을 같은 주기로 다시 그리지 않는다. [[게임-크롤러-일일-평론]]의 *"달라진 것만"* 형식 제안과 같은 원리다.
- **도트 사례 게임과의 대비.** 크롤러 상위권의 [[게임요소-사례-스타듀-밸리]]·[[게임요소-사례-테라리아]]는 손으로 찍은 2D 도트로 알려져 있다(일반 지식, 해당 페이지에서 렌더링 방식 미확인). 이 파이프라인은 같은 *보이는 결과* 를 3D 쪽에서 만든다. 두 길을 비교하면 1인 개발에서 *애니메이션 비용*을 어디서 줄일지 판단하는 데 도움이 된다.
