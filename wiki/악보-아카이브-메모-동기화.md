> [!tip] 핵심 takeaway
> 🧠 이 프로젝트에서 **유일하게 정말 까다로운 부분**. 나머지는 평범한 CRUD다.
> 🧠 해법의 한 줄 요약: **메모를 "덮어쓰기 대상"이 아니라 "append-only 이벤트"로 다룬다.** 그러면 오프라인 충돌이 구조적으로 발생하지 않는다.
> 📄 사용자 요구(D7): "캐싱해서 보여주되 중간에 인터넷 연결되면 새로고침 한다든지 — 그럼 그동안 작성한 메모도 없어지면 안 되겠지."

## 1. 메모는 세트가 아니라 곡에 붙는다 (📄 D1)

> [!warning] 🧠 원래 설계의 함정
> "주일 곡목을 하나의 PDF로 병합"(📄 초기 희망) + "사용자별 펜슬 메모 저장"을 그대로 합치면, 병합 PDF에 한 필기는 **그 주 세트 전용**이 된다. 다음 주에 같은 곡이 다시 나오면 필기가 따라오지 않는다. 실전에서 가장 아쉬울 지점.

📄 사용자 확정: **"보여줄 때 필기가 따라올 수 있게 악보별로 좌표로 붙이는 거 너무 좋아. 꼭 하나의 PDF일 필요는 없지."**

→ 메모는 `sheet_id` + `page` + 좌표로 저장하고, 뷰어가 악보 위에 **오버레이로 렌더링**한다. 병합 PDF는 "오프라인 백업용 다운로드"로만 남긴다.

## 2. 레이어 분리 (📄 D2)

| 레이어 | 작성자 | 보이는 사람 | 용도 |
|---|---|---|---|
| `shared` (공용) | 팀장 / 인도자 | 팀 전체 | 📄 송폼(D4), 반복 횟수, 전체 공지사항 |
| `personal` (개인) | 각 사용자 | 본인만 | 개인 큐, 파트 표시, 호흡 표시 |

- 🧠 뷰어에서 레이어를 **개별 on/off** 할 수 있게 한다. 공용만 켜고 보기, 내 것만 보기, 다 끄고 원본 보기.
- 🧠 `shared` 쓰기 권한은 `leader` role만 → [[악보-아카이브-인증-권한]] §4-2.

## 3. 데이터 구조 — append-only 스트로크 (🧠 핵심 설계)

> [!danger] 🧠 하면 안 되는 방식
> "이 악보의 메모 = 렌더링된 이미지 한 장"으로 저장하면, **마지막에 저장한 쪽이 이긴다.** 오프라인에서 쓴 메모가 온라인 복귀 시 통째로 날아가거나 서버 것을 덮어쓴다. 📄 사용자가 우려한 바로 그 사고.

### 채택 방식: 스트로크 1개 = 레코드 1개

```
annotations
├─ id            (클라이언트가 생성하는 UUID — 오프라인에서도 발급 가능)
├─ sheet_id      (곡. 세트 아님 — D1)
├─ team_id
├─ user_id
├─ page          (몇 페이지)
├─ layer         ('personal' | 'shared')
├─ kind          ('ink' | 'text' | 'song_form')
├─ payload       (ink: 좌표 배열+필압+색·굵기 / text: 내용+위치)
├─ deleted       (지우개 = 삭제가 아니라 true 표시)
├─ created_at    (클라이언트 시각)
└─ synced_at     (서버 도달 시각)
```

핵심 성질 (🧠):
- **id를 클라이언트가 만든다** → 오프라인에서 그린 것도 정식 id를 가진다. 재전송해도 중복이 안 생긴다(멱등).
- **수정이 없다, 추가만 있다** → 두 기기가 동시에 그려도 합집합이 정답. 충돌 해소 로직 자체가 불필요.
- **지우개도 추가다** (`deleted=true`) → 오프라인 삭제가 온라인 복귀 후 되살아나지 않는다.
- 좌표는 **PDF 페이지 기준 상대좌표(0~1)** 로 저장 → 화면 크기·확대율이 달라도 같은 위치에 찍힌다. ⚠️ 절대 픽셀로 저장하지 말 것.

## 4. 오프라인 동작 흐름 (📄 D7)

```
필기 발생
  → 즉시 로컬(IndexedDB)에 저장       ← 화면 반영은 항상 즉각. 네트워크와 무관
  → 온라인?
      ├─ 예: 백그라운드로 서버 전송
      └─ 아니오: 전송 대기열에 적재
연결 복구 감지
  → ① 대기열 전송 (실패해도 대기열에 남김)
  → ② 서버의 새 스트로크 수신
  → ③ 로컬 = 로컬 ∪ 서버   (합집합. 어느 쪽도 덮어쓰지 않음)
```

> [!warning] 🧠 반드시 지킬 것 — 새로고침 대상 분리
> **악보 파일(PDF)의 새로고침**과 **메모의 동기화**를 하나로 묶으면 📄 사용자가 우려한 사고가 그대로 난다.
> - 악보 PDF: 거의 안 바뀜 → 통째로 교체해도 안전
> - 메모: 절대 통째로 교체 금지 → 항상 병합
> 이 둘의 주기와 방식을 코드상에서 분리한다.

## 5. 캐싱 전략 (🧠)

- **"이번 주 세트만 캐싱"** 을 기본으로 한다. 전체 아카이브를 캐싱하려 하지 않는다.
  - 🧠 이유: iOS Safari는 웹 저장 공간을 제한하고, 오래 안 쓴 사이트의 데이터를 정리할 수 있다. 악보 PDF는 무겁다.
  - 홈 화면에 추가된 PWA는 조건이 나은 편이지만 무제한은 아니다 → [[악보-아카이브-뷰어-배포]] §PWA 제약
- 메모(스트로크)는 용량이 작으므로 **전량 로컬 보관**해도 부담 없다.
- 🧠 세트 열람 시 **선제 캐싱(prefetch)**: 팀원이 예배 전 링크를 한 번 열면 그 세트 전곡을 미리 받아둔다. 주일 아침 와이파이가 죽어도 예배가 돌아간다.

## 6. 개발 시 체크리스트 (🧠)

- [ ] 스트로크 id는 반드시 **클라이언트 생성 UUID**
- [ ] 좌표는 **상대좌표(0~1)**, 절대 픽셀 금지
- [ ] 전송은 **멱등**하게 (같은 id 재전송 시 무시 또는 upsert)
- [ ] 대기열은 전송 성공 확인 후에만 비움
- [ ] 악보 PDF 갱신과 메모 동기화의 **코드 경로 분리**
- [ ] 앱 강제 종료 / 배터리 방전 시 로컬 저장이 살아있는지 확인 (IndexedDB 즉시 flush)
- [ ] `deleted` 스트로크의 정리(compaction) 정책 — 무한히 쌓이지 않게
- [ ] 페이지 수가 바뀐 악보로 교체됐을 때 기존 메모 좌표 처리 (⚠️ 🧠 놓치기 쉬움. 초안: 교체 시 경고 + 메모 보존하되 "원본 변경됨" 표시)
