> [!tip] 핵심 takeaway
> 📄 사용자 지시: **"로그인 부분 잘 정의해둘 것 — 나중에 개발할 때 빼먹지 않도록. 팀 아이디도 마찬가지."** 이 페이지가 그 정의서다.
> 🧠 결론 1 — **카카오 로그인은 문제없이 쓸 수 있다.** 이 서비스는 이메일·전화번호가 필요 없고 **회원번호 + 닉네임만** 쓰면 되는데, 이 둘은 비즈 앱 전환 없이 사용 가능하다.
> 🧠 결론 2 — **`team_id`는 MVP 첫 스키마부터 넣는다.** 지금은 공짜지만 나중에 붙이면 마이그레이션이 아프다.

## 1. "자동 로그인"의 두 가지 의미 (🧠 반드시 구분할 것)

📄 사용자 요구는 "로그인이 자동으로 되면 참 좋다"였는데, 여기엔 서로 다른 두 가지가 섞여 있다. **설계 시 반드시 분리한다.**

| 구분 | 의미 | 난이도 | 결정 |
|---|---|---|---|
| **A. 재방문 자동 로그인** | 한 번 로그인한 사람은 다시 로그인하지 않아도 됨 | 쉬움 | ✅ 채택. 세션 토큰 장기 유지(예: 90일) + 자동 갱신 |
| **B. 최초 방문 무로그인 열람** | 링크를 처음 누른 사람이 로그인 없이 바로 봄 | 메모 기능과 충돌 | ⚠️ 조건부 채택 (아래 §2) |

> [!warning] 🧠 B가 메모와 충돌하는 이유
> 메모는 "누가 썼는지"를 알아야 저장된다. 익명 사용자에게는 개인 메모를 붙일 주체가 없다. 따라서 **읽기는 익명 허용, 쓰기는 로그인 요구**로 가른다.

## 2. 접근 정책 (🧠 확정 제안)

```
링크 탭
 ├─ 이미 로그인됨 (대부분)     → 곧바로 곡목 화면. 마찰 0
 └─ 로그인 안 됨
     ├─ 악보 열람           → 허용 (읽기 전용)
     └─ 메모하려고 펜을 듦   → 이때 로그인 요청
```

- 🧠 "일단 열어본다"는 부담이 없고, 로그인은 실제로 필요한 순간에만 요구된다.
- 🧠 팀장은 새 팀원에게 링크만 던지면 된다 (별도 초대 절차 없이도 첫 진입 가능).
- ⚠️ 단, 세트 링크는 **추측 불가능한 토큰**(UUID 등)을 써야 한다. 링크를 아는 사람은 볼 수 있다는 뜻이므로, 민감도 판단은 팀장 몫 → §5 참조.

## 3. 로그인 수단 — 카카오 로그인 검토 결과 (📄 지시로 조사, 2026-08-27)

📄 사용자 우려: **"카톡 로그인이 잘 될지 걱정되는 부분이 있으니 검토해줘. 어려우면 자체 로그인 시스템을 만들어야 해서."**

### 3-1. 조사 결과 — 동의항목과 비즈 앱 전환

📄 카카오 developers 문서 기준:

| 동의항목 | 비즈 앱 전환 필요? |
|---|---|
| **회원번호(고유 ID)** | ❌ 불필요 |
| **프로필 정보 (닉네임 · 프로필 사진)** | ❌ 불필요 |
| 카카오계정 이메일 | ✅ 필요 |
| 이름 · 전화번호 · 생일 · 성별 · 연령대 | ✅ 필요 |

📄 비즈 앱 전환 요건: **개인 개발자도 가능**하다 (개인 개발자 본인인증 완료 + 비즈니스 정보 심사 승인). 심사는 영업일 3~5일 소요.

### 3-2. 결론 (🧠)

> [!tip] ✅ 카카오 로그인 채택 가능 — 비즈 앱 전환 불필요
> 이 서비스가 사용자에게서 필요한 정보는 **① 이 사람이 누구인지 구분할 고유값 ② 화면에 표시할 이름**뿐이다. 이메일도 전화번호도 쓸 데가 없다.
> → **회원번호 + 닉네임**만 받으면 되고, 이 둘은 **비즈 앱 없이 기본 제공**된다. 즉 심사·사업자등록 없이 바로 붙일 수 있다.

- 🧠 채택 이유: 비밀번호가 없고, 팀원 대부분이 이미 카톡에 로그인돼 있어 탭 2번이면 끝난다. 20명 규모 교회 팀에 마찰이 가장 적다.
- 🧠 주의: 회원번호는 **앱 단위로 고유**하다. 앱을 새로 파면 기존 사용자 매칭이 깨지므로 **앱을 처음부터 하나로 확정**하고 옮기지 않는다.
- 🧠 주의: 닉네임은 사용자가 언제든 바꾼다. 팀 명단 표시는 닉네임을 초기값으로 쓰되, **서비스 내 표시 이름(`display_name`)을 따로 저장**해 팀장이 수정할 수 있게 한다. (예: 카톡 닉네임이 "🌸봄🌸"이어도 팀 명단엔 "김찬양")

### 3-3. 대비책 — 자체 로그인 (🧠)

📄 사용자가 "어려우면 자체 로그인을 만들어야 한다"고 했으므로, 대비책을 함께 정의한다.

- 🧠 **권장: 처음부터 인증을 추상화**한다. `users` 테이블에 `auth_provider`(`kakao` / `local`) + `provider_uid` 컬럼을 두면, 카카오가 막히거나 정책이 바뀌어도 자체 로그인을 **추가**만 하면 된다. 이러면 "카카오냐 자체냐"를 지금 결정하지 않아도 된다.
- 🧠 자체 로그인이 필요해질 경우의 형태: [[콜링]]과 동일한 방식(이름 + 소속 + 생년월일 + 비밀번호 + 관리자 승인제)을 재사용하면 교회 맥락에서 일관성이 있다.
- 🧠 Supabase를 쓰면 Auth가 카카오 OAuth와 이메일/비밀번호를 모두 지원하므로 이 추상화가 거의 공짜다.

> [!danger] ⚠️ Supabase Auth = AWS 이전 시 유일한 진짜 락인 지점
> 📄 프로토타입은 Supabase지만 **운영은 AWS 유력**([[악보-아카이브-데이터-모델]] §1-1). DB·스토리지·RLS는 그대로 옮겨가지만 **Auth만은 대응물이 다르다**(Cognito 또는 자체).
> 🧠 그래서 규칙: **`auth.users`에 직접 조인하거나 Supabase JWT 구조에 의존하지 않는다.**
> - 서비스의 정본은 **자체 `users` 테이블**이다. Supabase Auth는 "카카오 OAuth를 대신 처리해주는 도구"로만 쓴다.
> - 로그인 성공 시 `provider_uid`(카카오 회원번호)로 자체 `users`를 찾거나 만든다.
> - 이렇게 해두면 나중에 Cognito로 갈아끼우든 자체 로그인을 만들든 **`provider_uid` 매칭만 유지**하면 사용자 데이터가 그대로 살아난다.
> - ⚠️ 반대로 이걸 어기면 **사용자·메모 데이터가 Supabase에 발이 묶인다.** 이전 비용이 가장 큰 항목.

> [!note] 🧠 프로토타입 단계에서는
> 📄 프로토타입은 단독 개발이므로 **로그인 구현 자체를 생략하고 하드코딩된 사용자 1명**으로 시작해도 된다. 이 페이지의 정의는 "나중에 빼먹지 않기 위한 명세"이지 프로토타입 필수 구현 목록이 아니다.
> 🧠 단, **`team_id`만은 프로토타입 스키마에도 넣는다** (§4 참조). 소급 적용이 가장 아프다.

## 4. `team_id` — 팀·부서 구조 (📄 지시로 별도 정의)

📄 요구사항 9번 "로그인 및 회원관리 필요 / 부서별 관리" + 📄 "나중에 비슷한 규모의 찬양팀이 여러 개 추가될 수 있음(추후 고려)".

> [!warning] 🧠 지금 당장 UI를 만들지는 않되, 스키마에는 반드시 넣는다
> 멀티팀 **화면**은 나중에 만들어도 되지만, **`team_id` 컬럼은 첫 마이그레이션부터** 넣는다. 나중에 넣으려면 기존 모든 행에 소급 적용 + 모든 쿼리 수정 + 권한 재설계가 동시에 필요해진다. 지금 넣으면 비용이 0에 가깝다.

### 4-1. 규약 (🧠 확정 제안)

1. **`team_id`를 갖는 테이블**: `sheets`(악보), `sets`(곡목), `memberships`, `annotations`(메모) — 즉 **팀에 귀속되는 모든 데이터**.
2. **모든 조회 쿼리는 `team_id`로 필터**한다. 예외를 만들지 않는다.
3. **`users`는 `team_id`를 갖지 않는다.** 한 사람이 여러 팀에 속할 수 있어야 하므로 `memberships`(user × team × role)로 푼다. — 🧠 지금은 한 팀뿐이지만 이 구조가 나중에 "찬양팀 + 청년부 찬양팀 겸직"을 공짜로 처리한다.
4. **MVP에서는 팀을 1개만 생성**하고 UI에 팀 전환을 노출하지 않는다. 데이터만 올바르게 쌓아둔다.
5. Supabase를 쓴다면 **RLS 정책을 `team_id` 기준으로** 처음부터 건다. 나중에 거는 것보다 훨씬 안전하다.

### 4-2. 역할(role) 정의 (🧠 초안)

| role | 권한 |
|---|---|
| `leader` (팀장) | 악보 업로드·수정, 세트 생성·배포, 멤버 승인·역할 변경, 공용 메모 작성 |
| `member` (팀원) | 악보 열람, 개인 메모 작성, 공용 메모 열람 |
| `admin` (관리자) | 팀 생성, 팀 간 관리 (추후) |

- 🧠 "부서별 관리"(📄 요구사항 9)는 팀보다 상위 개념일 수 있다. 교회 조직상 `부서 > 팀` 구조인지 확인 필요 → **⏳ 사용자 확인 대기**. 필요하면 `departments` 테이블을 `teams` 위에 한 겹 더 둔다.

## 5. 개발 시 빠뜨리기 쉬운 항목 체크리스트 (🧠)

📄 "나중에 개발할 때 빼먹지 않도록" 요청에 대한 응답.

- [ ] 세션 토큰 장기 유지 + 자동 갱신 (재방문 자동 로그인의 실체)
- [ ] 로그인 후 **원래 보려던 링크로 복귀**(redirect back) — 이거 빠뜨리면 링크 타고 들어와 로그인한 뒤 홈으로 튕긴다. 체감 품질에 직결
- [ ] 카톡 인앱 브라우저 대응 → [[악보-아카이브-뷰어-배포]] §카톡 인앱 브라우저 (⚠️ 여기서 세션이 갈린다)
- [ ] 세트 링크 토큰은 추측 불가능하게 (UUID v4 이상)
- [ ] 링크 만료 정책 정하기 (🧠 초안: 만료 없음. 지난 곡목 다시 보기가 이 서비스의 강점이므로)
- [ ] `auth_provider` / `provider_uid` 추상화 (자체 로그인 대비)
- [ ] `display_name` 별도 저장 (카톡 닉네임 변경 대비)
- [ ] 탈퇴·재가입 시 기존 메모 처리 정책
- [ ] 팀장 권한 이양 경로 (팀장이 교회를 옮기면?)
- [ ] `team_id` 필터 누락 방지 — RLS 또는 공통 쿼리 레이어로 강제
- [ ] 첫 진입 사용자의 팀 배정 방법 (🧠 초안: 세트 링크로 들어오면 그 세트의 팀에 `pending` 멤버십 생성 → 팀장 승인)
