### Cogi v0.16.2 릴리스 📄
- 화면·사용법은 그대로다. npm audit 29건이 0건이 됐다.
- 릴리스 규약 6단계를 모두 마쳤다: 코드·태그·GitHub Release → DB(변경 없음) → 엣지 함수(변경 없음) → 프론트(배포 플랫폼 + 사내 서버) → 공개 개요 페이지 + 아티팩트 → 로드맵.

## 5. 같은 날 정리한 것

### 5-1. JDK 누락 점검 📄🧠
- 사용자 질문: "요즘 JDK 취약점 얘기가 도는데 왜 안 찾아줬나?"
- 📄 원인 1: 이날 일괄 점검은 npm만 봤다.
- 📄 원인 2: 자동 점검의 CVE 감시 제품명에 Java 계열이 없었다.
- 📄 원인 3: 실측 스냅샷은 컨테이너 **이미지 이름**만 봐서, 미들웨어 이미지 안에 들어 있는 런타임(JDK)을 알 수 없었다. 실제로 사내 검색 엔진 이미지에 영향 범위의 JDK가 들어 있었다.
- 조치: 감시 제품명에 Java SE·OpenJDK·Temurin을 추가했다. 🧠 앞으로 새 미들웨어 이미지가 들어오면 **안에 든 런타임(JDK·Python 등)도 자산 목록에 같이 적는다.**
- 개인 맥의 JDK 23은 지원이 끝난 버전이라 LTS(25)로 바꿀지 검토 중이다.

### 5-2. 조치 범위: "내가 올린 것만" 📄
- 사용자 결정: **"내가 올린 것만 수정할 거야. 이미 있던 건 수정 안 할 거야."**
- 조치 대상: 개인 저장소, 내가 배포한 앱, 사내 클러스터에서 내 네임스페이스, 개인 맥.
- 조치하지 않는 것: 내가 오기 전부터 있던 공용 구성(사내 DB·검색 엔진·캐시·제품 서비스 이미지, 다른 팀 서버). 영향이 있어도 "담당 영역(조치 없음)"으로 참고만 적는다.
- 자동 점검(평일 07:00, [[보안-취약점-공지-모음]])의 판정 프롬프트 맨 앞에 이 규칙을 넣었다. 그래서 기존 구성 영향은 긴급 카드로 올라오지 않는다.
- 🧠 이렇게 두면 알림이 "내가 실제로 고칠 수 있는 것" 위주로 줄어든다. 기존 구성 쪽은 사실만 기록해 두었다가 담당 쪽에 전달할 때 근거로 쓴다.

## 6. 배운 점
- 🧠 **직접 의존성만 보면 놓친다.** Cogi에서는 개발 CLI(shadcn)를 거쳐 들어온 전이 의존성이 운영 취약점으로 잡혔다. 자동 점검의 저장소 스캔도 lock 파일의 전이 의존성까지 보도록 넓히는 게 다음 과제다.
- 🧠 **패치가 끊긴 패키지는 버전 올리기로 해결되지 않는다.** npm의 `xlsx`처럼 공식 배포처가 옮겨 간 경우에는 공급처를 바꿔야 한다. 이때는 빌드 환경(사내 서버)에서 새 공급처에 접근할 수 있는지가 배포 조건이 된다.
- 🧠 **감시 목록은 "내가 설치한 것"이 아니라 "실제로 돌고 있는 것"을 기준으로 적어야 한다.** 이미지 안에 내장된 런타임은 이미지 이름에 드러나지 않는다.
- 🧠 **조치 범위를 먼저 정해 두면 판단이 빨라진다.** 무엇을 고칠지 매번 따지지 않고, 범위 밖은 기록만 한다.
