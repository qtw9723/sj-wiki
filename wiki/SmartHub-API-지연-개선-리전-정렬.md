> [!tip] 핵심 takeaway (포트폴리오 관점)
> ⭐ **Vercel 함수가 미국 동부에서 돌며 도쿄 DB를 조회하고 있었다. 설정 한 줄로 DB 1회 조회 API의 응답 시간이 p50 891ms에서 137ms로 85% 줄었다.** 이어서 사내판과 비교해 남은 차이를 "순차 단계 수 × 조회 1회 비용"으로 설명하고 백오피스 조회를 병렬화했다(2단계). 백오피스 체감은 약 2초에서 "확실히 빨라짐"으로 바뀌었다(사용자 확인).
> 팔 포인트는 숫자보다 진단 과정이다. (1) "keep-alive로 될까"라는 처음 가설을 구간별로 따져 기각하고 (2) 원인 후보를 효과·확인 비용 순으로 세운 뒤 (3) 설정값이 아니라 **응답 헤더에 찍힌 실제 실행 리전**을 근거로 삼았고 (4) DB를 안 쓰는 엔드포인트를 대조군으로 같이 재서 개선분을 DB 왕복과 네트워크 거리로 나눠 설명했다.

## 상황 (Situation)
📄 SmartHub 외부판(Vercel + Supabase)에서 화면이 전반적으로 느리다는 체감이 계속 있었다. 사용자가 처음 던진 질문은 "HTTP keep-alive라는 기술로 이 문제를 풀 수 있나"였다.

## 과제 (Task)
🧠 느린 원인을 찾아 근거가 있는 개선을 하고, 전후를 숫자로 보여 줄 것. 사용자 지시는 "1번(리전)을 우선 적용해 보고 테스트해 봐, 프로젝트는 아무거나"였다.

## 행동 (Action)

### 1. 첫 가설 기각: keep-alive
🧠 구간별로 나눠 보니 keep-alive는 이미 적용돼 있거나 손댈 수 없는 구간이었다.

| 구간 | 상황 |
|---|---|
| 브라우저 → Vercel·Supabase | HTTP/2·3라 연결 재사용이 기본 |
| 함수 → Supabase REST | supabase-js의 fetch(undici)가 이미 재사용, 콜드 스타트 때만 새 연결 |
| 함수 → Postgres 직접 연결 | 이 경우만 해당 → keep-alive가 아니라 커넥션 풀러(Supavisor)가 답 |

### 2. 원인 후보를 순서대로 세움
🧠 체감 효과가 크고 확인 비용이 작은 순서: **리전 불일치** → 순차 쿼리(워터폴) → 콜드 스타트 → RLS 정책 비용(`auth.uid()` 행마다 평가) → 인덱스 누락 → 무료 플랜 일시정지.

### 3. 진단: 설정이 아니라 실제 실행 리전을 본다
- 📄 DB 위치: Supabase Management API → `ap-northeast-1`(도쿄)
- 📄 함수 위치: Vercel API 토큰이 만료돼 설정 조회가 막혔다. 대신 응답 헤더 `x-vercel-id: <엣지>::<함수리전>::<id>`로 확인했다.
  - SmartHub `icn1::iad1` → 서울 엣지, **함수는 미국 동부**
  - 같은 계정의 [[led-quiz]] `icn1::hnd1` → 이미 도쿄
  - [[CogInsight-Generator|Cogi]]는 함수가 없는 정적 SPA라 대상에서 제외

```
변경 전: 서울 → 서울 엣지 → 미국 동부(함수) ⇄ 도쿄(DB) → 서울
변경 후: 서울 → 서울 엣지 → 도쿄(함수)     ⇄ 도쿄(DB) → 서울
```

### 4. 대조군을 둔 측정
- 🧠 엔드포인트 둘을 같이 쟀다. `/api/hubs/cs`는 인증 없이 DB를 한 번 조회하고, `/api/health`는 DB를 쓰지 않는다. 둘의 차이가 **DB 조회 1회에 붙는 비용**이 된다.
- curl `time_starttransfer`(첫 바이트까지 시간) 30회, 응답마다 함수 리전도 기록. 재사용할 수 있게 저장소에 `scripts/bench-ttfb.sh`로 남겼다.

### 5. 적용
- `vercel.json`에 `"regions": ["hnd1"]` 한 줄. JSON 전체를 다시 직렬화하면 diff가 커져서 원래 포맷을 살리고 한 줄만 넣었다.
- 메인 체크아웃이 다른 작업(도메인 변경 브랜치) 중이라 `origin/main` 기준 별도 워크트리에서 작업했다.
- 프리뷰 배포는 Vercel 로그인 보호(302)로 외부 측정이 불가능했다. 되돌리기가 PR revert 한 번이라 **사용자 승인 후** 프로덕션에 머지했다. 자동 모드가 프로덕션 배포를 한 번 막았고, 우회하지 않고 사용자 확인을 받았다.

## 결과 (Result)
📄 서울에서 각 30회 측정한 결과.

| 엔드포인트 | 변경 전 p50 / p90 (`iad1`) | 변경 후 p50 / p90 (`hnd1`) | p50 개선 |
|---|---|---|---|
| `/api/hubs/cs` (DB 1회) | 891 / 991ms | **137 / 164ms** | **-85%** |
| `/api/health` (DB 없음) | 256 / 290ms | 102 / 131ms | -60% |

- DB 1회 조회에 붙던 비용이 **약 635ms에서 약 35ms로** 줄었다.
- DB를 안 쓰는 요청도 빨라졌다. 엣지에서 함수까지 거리가 줄었기 때문이다.
- 배포 직후 첫 측정의 p90 튐(429ms)은 재측정에서 사라져 콜드 스타트로 판단했다.
- 🧠 화면 하나가 API를 여러 번, API 하나가 DB를 여러 번 부르면 조회 횟수만큼 약 600ms씩 줄어든 셈이다. Supabase pg_cron이 부르는 정시 작업도 이제 DB와 같은 리전에서 돈다.

## 배운 것 🧠
- **권장 사항을 아는 것과 실제 배포를 확인하는 것은 다르다.** 저장소 `CLAUDE.md`에 이미 "함수 리전을 주 데이터 소스 가까이 두라"는 Vercel 권장이 적혀 있었는데, 실제 배포는 기본값으로 돌고 있었다.
- **설정 대신 관측값으로 확인한다.** 권한이 막혀도 응답 헤더로 사실을 확인할 수 있었고, 배포 후 검증도 같은 방법으로 했다.
- **개선을 말할 때는 대조군을 둔다.** "빨라졌다"를 원인별로 나눠 설명할 수 있어야 다음 개선 지점이 보인다.
- **기술 이름에서 출발하지 말고 구간에서 출발한다.** keep-alive는 맞는 기술이었지만 이 구조에서 병목은 아니었다.

## 남은 것
- 측정 위치는 서울 한 곳뿐이다(사용자가 국내라 충분하다고 판단).
- 원인 후보 중 리전과 백오피스 첫 화면의 순차 조회를 처리했다. 다른 화면이 느리면 다음은 그 라우트의 순차 쿼리, RLS 정책(`(select auth.uid())`·인덱스)이다.
- 같은 Supabase를 쓰는 다른 Vercel 앱에 함수를 새로 올릴 때도 `regions: ["hnd1"]`을 기본으로 둔다.

## 2단계: 순차 조회 병렬화 (같은 날, PR #81)
📄 리전을 맞춘 뒤 사용자 체감은 "빨라지긴 했는데 사내 서버 속도는 아니다"였다. 같은 코드가 사내판(k8s)에서는 백오피스 모듈 로딩이 0.2~0.3초였다.

🧠 사내판이라는 비교 기준이 있어서 원인을 좁히기 쉬웠다.

| 환경 | DB 접근 | 조회 1회 비용 |
|---|---|---|
| 사내판 | 같은 클러스터 Postgres에 직접 연결 | 1ms 안팎 |
| 외부판 | Supabase REST(HTTPS) | 약 35ms (📄 1단계 측정값의 차이) |

📄 백오피스 서버는 조회를 하나씩 기다리고 있었다. `/overview`는 허브 × 모듈 요약을 `for … await`로 돌아 약 10단계, `/activity`는 7단계였다.

🧠 **체감 지연 ≈ 순차 단계 수 × 조회 1회 비용.** 1단계(리전)는 뒤쪽을 줄였고 2단계는 앞쪽을 줄였다. 같은 코드가 사내판에서 빨랐던 것도 이 식으로 설명된다.

- 📄 `Promise.all`로 overview 약 10단계 → 3단계, activity 7단계 → 2단계. 소스별 실패 처리·응답 순서는 그대로 두었다.
- 📄 TDD: 응답을 손으로 풀어 주는 가짜 쿼리로 "앞 조회가 끝나기 전에 다음 조회가 출발하는가"를 테스트로 만들어 먼저 실패를 확인하고 고쳤다. 기존 테스트가 DB 호출 순서에 맞춰 가짜 응답을 넣는 방식이라 호출 **출발 순서**는 예전과 같게 유지했다.
- 📄 **결과 (2026-11-12, 사용자 확인)**: 배포 후 외부판 백오피스를 다시 열어 본 사용자 평가는 "확실히 빨라졌다"였다. 변경 전에는 모듈 로딩이 체감상 2초 가까이 걸렸다. 수치 측정은 하지 못했다. 백오피스가 마스터 키로 보호돼 있고, 틀린 키로 시도하면 로그인 시도 제한에 걸리기 때문이다.
- 🧠 배운 점: 개발 환경이나 사내 환경처럼 DB가 가까운 곳에서는 순차 조회가 드러나지 않는다. **조회 비용이 큰 환경에서 처음 문제로 보인다.**

## 후속: 다른 프로젝트 전수 점검 (같은 날)
📄 같은 방법(응답 헤더 `x-vercel-id` + Supabase 리전)으로 로컬 Vercel 프로젝트 8개를 모두 확인했다.
- 함수와 DB가 어긋난 곳은 SmartHub뿐이었다. [[led-quiz]]는 원래 `hnd1`이었다.
- [[CogInsight-Generator|Cogi]]·[[notepad]]·market-board·[[Bible-Quest]]는 서버 함수가 없는 정적 페이지라 해당 없다. 브라우저가 Supabase를 직접 부른다.
- sj-wiki RAG API는 `iad1`이지만 DB 없이 로컬 인덱스만 읽어 요청당 약 150ms 차이뿐이다. 사용자 판단으로 그대로 두었다.

🧠 **일반화한 점검 순서** (Vercel·Netlify 같은 서버리스 + 관리형 DB 조합 어디에나 적용):
1. DB 리전을 확인한다.
2. 함수가 **실제로** 어디서 도는지 응답 헤더로 확인한다(설정이 아니라 관측값).
3. 둘이 다르면 함수 리전을 DB 쪽으로 옮긴다. 사용자 쪽이 아니다. 함수와 DB 사이 왕복이 요청 하나에 여러 번 일어나기 때문이다.
4. DB를 쓰는 엔드포인트와 안 쓰는 엔드포인트를 같이 재서 전후를 비교한다.
