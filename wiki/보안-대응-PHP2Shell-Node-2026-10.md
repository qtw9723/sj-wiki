> [!tip] 핵심 takeaway
> 🧠 **"빠르게 분석하고, 빠짐없이 조사하고, 안전하게 바꾸고, 모르는 것은 모른다고 쓴다"를 한 사건으로 보여 주는 포트폴리오 사례.** [[프로젝트-포트폴리오]]의 개발 프로젝트들이 *만드는 역량*이라면, 이건 *운영을 지키는 역량*이다.
> 📄 실제 악용 중인 PHP 원격 코드 실행 취약점(CVSS v4 9.2)을 2일(2026-10-27~28) 안에 단독으로 분석·전수 조사·패치했고, 같은 시기의 Node.js 보안 릴리스까지 함께 정리했다.

## 1. 상황 📄
- **PHP2Shell**(CVE-2026-109618·109619, CVSS v4 9.2): POST 요청 하나로 인증 없이 원격 코드 실행(RCE). 요청 파싱 중 메모리 고갈을 처리한 뒤 해제된 메모리를 다시 쓰는 Use-After-Free. 앱 코드가 실행되기 전 단계라 앱 인증으로는 막을 수 없고, 임시 설정만으로는 해결되지 않아 패치가 해법.
- 패치 버전 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12(2026-10-21 배포). 공개 4일 전(10/17)부터 실제 악용 관측, 10/26 CISA KEV(악용 중 취약점) 등재.
- **Node.js 10월 보안 릴리스**: 취약점 10건, 최고 High. 내장 Brotli 디코더 범위 밖 쓰기, TLS 호스트명 검증 우회, DNS NUL 바이트 처리가 핵심. 패치 버전 22.23.4 / 24.22.1 / 26.12.1. 실제 악용 보고 없음.
- 내 역할: 이슈 분석·전수 조사·침해 점검·패치·검증을 단독 수행. 범위는 로컬 저장소 19개, 서버(컨테이너), 배포 플랫폼 프로젝트 10개, CI 파이프라인.

## 2. 조사 방법 📄
원칙은 **코드가 아니라 실제로 돌고 있는 런타임 버전 기준**.
- 저장소: PHP 파일·composer 유무, `.nvmrc`·`.node-version`·`engines`·Dockerfile `FROM`·CI `node-version` 고정값.
- 서버: 컨테이너 안에서 `php -v`·`node -v`, 포트 노출(0.0.0.0:80 여부), `php -i`로 취약 관련 설정.
- 배포 플랫폼: 프로젝트별 Node 버전과 마지막 배포 시점.
- 코드: 취약 API(Brotli 해제·`checkServerIdentity`·`dns.resolve`) 직접 사용 없음. `fetch`가 Brotli 응답을 받는 경로가 있어 버전 상향으로 대응.

| 대상 | 상태 | 위험도 |
|---|---|---|
| 인터넷 공개 PHP 운영 서버(클라우드 VM·Docker) | PHP 8.4.16, 인터넷 공개, upload_progress 켜짐 | Critical |
| 로컬 개발 환경 | Node 25.4.0(지원 종료), 정기 자동화가 이 버전으로 실행 | 중간 |
| 협업 저장소 | Node 24.19.0 정확 고정(CI·배포 이미지 digest 포함) | 중간 |
| 배포 플랫폼 3개 | 마지막 배포가 패치 이전(최대 141일 전) | 낮음 |
| 개인 프로젝트 Dockerfile | node:20(지원 종료), 빌드 단계만 | 낮음 |
| 배포 플랫폼 7개·GitHub Actions | 패치 이후 배포 / 최신 22.x 자동 적용 | 안전 |
| Supabase Edge Functions | Deno 런타임이라 해당 없음 | 해당 없음 |

## 3. 침해 흔적 점검 📄 (패치 전에 먼저, 10/15 이후)
에러 로그의 메모리 고갈·세그폴트 0건, 세션 파일 1,035개의 `upload_progress`·PHP 코드 삽입 0건, 접근 로그의 비정상 대용량 POST·스캔 없음, 웹 프로세스 아래 셸 없음 → **발견 없음**.
- ⚠ 한계: 접근 로그에는 요청 본문이 남지 않는다. "흔적 없음"이지 100% 보장이 아니다.

## 4. 조치 절차(운영 서버) 📄
1. 공식 이미지가 10/26에 재빌드된 것 확인 → 2. 새 이미지로 교체 전 임시 컨테이너 검증(함께 든 Node 22.23.4) → 3. 데이터가 named volume에 있어 교체해도 보존 → 4. DB 전체 덤프(34MB, 완료 확인)와 sites 볼륨 백업 → 5. 기존 이미지에 롤백 태그 → 6. 앱 컨테이너만 재생성(DB 컨테이너 유지) → 7. 검증: 컨테이너 안 PHP 8.4.27, 로그인 페이지 내부·외부 HTTP 200, 기동 로그 정상. 재생성 직후 약 40초는 기동 중이라 응답 없음.

**Node 조치**: 로컬 25.4.0→26.12.1. 협업 저장소 24.19.0→24.22.1(`.nvmrc`·`engines`·`packageManager`·검사 스크립트·CI 이미지·배포 이미지 digest 동시 변경). 검증은 공식 배포본 SHA-256 대조 → 설치 → 타입 검사 → 빌드 → 전체 테스트(5,999건 통과, 실패 3건은 변경 전에도 동일). 배포 플랫폼 3개 재배포(HTTP 200), Dockerfile node:20→node:24. 부수 발견: npm 11.19부터 의존성 설치 스크립트가 승인 전에는 실행되지 않음(빌드 영향 없음).

## 6. 배운 점·개선 과제
- 📄 정확한 버전 고정은 재현성은 좋지만 보안 패치가 늦어진다 → 패치 릴리스 알림을 정기 점검에 넣는다.
- 📄 인터넷에 열린 서버는 보안그룹 접근 IP 제한과 HTTPS가 필요하다.
- 🧠 서술 규칙: [[프로젝트-포트폴리오]]의 수치 서술 규칙과 같은 결 — "발견 없음"과 "안전함"을 한 문장에 섞지 않는다.

## ⚠ 확인 필요
- 임시 설정(`session.upload_progress.enable` 관련) 문장은 원문이 잘려 "임시 설정만으로는 해결되지 않음"으로만 요약했다.
- 대상 서버는 회사 업무 서버다. 이 vault에는 일반화한 요약만 두고, 서버 식별 정보·운영 정보 같은 상세는 `sj-wiki-work`에만 둔다([[내-프로필]]·CLAUDE.md §1 기밀 분리 원칙). 공개 게시는 사용자 확인 완료(2026-10-28, 회사 허락 불필요).
