> [!tip] 핵심 takeaway
> 🧠 [[보안-대응-PHP2Shell-Node-2026-10]]이 "한 사건을 빠르게 막은" 사례라면, 이건 **"공지를 기다리지 않고 먼저 찾고, 같은 절차로 여러 저장소를 한 번에 고친"** 사례다. 탐지(자동 수집 확장) → 판단(KISA·CVE.org·OSV 차이 이해) → 조치(저장소 5곳 병렬 패치) → 전달(타팀용 점검 문서)까지 한 흐름으로 보여 줄 수 있다.
> 📄 하루(2026-11-16) 안에 Node.js 11월 보안 릴리스, PostgreSQL CVE 52건, nodemailer 수신 도메인 우회 취약점을 내 프로젝트 5곳에 반영했고, 사내 제품의 오픈소스 1,649개를 전수 대조해 담당팀 전달 문서를 만들었다.

## 1. 상황 📄
- **Node.js 11월 보안 릴리스**(KISA 2026-11-12 공지, 10건 + CVE.org 추가 8건): 해결 버전 22.23.5 / 24.22.3 / 26.13.1. 10월에 올린 22.23.4 / 24.22.1 / 26.12.1보다 한 단계 높아 **10월 조치분이 다시 영향 범위**에 들어갔다. 일부(CVE-2026-123863·123874)는 24.22.0 이상에서만 생겨, 10월에 맞춘 24.22.1이 정확히 걸렸다.
- **PostgreSQL CVE 52건**(CVE.org, 11월 둘째 주 공개): DB 사용자 권한으로 임의 코드 실행(CVSS 8.8), pg_restore 경유 코드 실행, 행 보안 정책 우회 등. 17 계열 해결 17.12. **KISA에는 공지가 없었다.**
- **nodemailer CVE-2026-125755**: 주소 파서가 공백 접기·주석에서 도메인을 잘라 수신 도메인 허용 검사를 우회한다. 공개 PoC가 있다. 해결 10.4.1.
- 같은 날 사내 제품(서비스 22개)의 오픈소스 목록을 받아 전수 점검했다(§4).

## 2. 탐지 방식 — 공지 수집 자동화 확장 📄
기존 자동 수집([[보안-취약점-공지-모음]], 평일 07:00 KISA 수집·자산 대조)에 **CVE.org 수집**을 붙였다.
- 원본: CVE 공식 목록의 변경 기록(GitHub `CVEProject/cvelistV5`의 deltaLog). 지난 실행 이후 **새로 공개된 CVE만** 받는다. 하루 약 500건, 받는 데 수 초.
- **자산 필터**: 감시 제품명(서버 구성요소) + 내 저장소의 npm·pip 패키지 이름 + 사내 제품 패키지 목록과 **정규화 후 이름이 같을 때만** 통과. 설명문 검색은 하지 않는다. 오탐 원인이던 것(scope 패키지의 뒷부분 `core`·`schema`, 다른 생태계의 같은 이름, 3글자 미만 이름)은 규칙으로 막았다.
- **제품별 묶음**: PostgreSQL 52건이 알림 52개가 아니라 1개가 되도록 같은 제품끼리 묶는다. 시험 결과 2주치 7,800여 건 → 12~18묶음.
- 정리는 한국어로 하고 기존 판정·매일 재점검·닫힘 흐름을 그대로 탄다. 🧠 걸러진 목록 자체가 자산 구성을 드러내므로 **이 vault(공개)에는 싣지 않고** 비공개 기록·브리핑에만 싣는다.

### 출처별 역할 차이 📄
| 출처 | 다루는 범위 | 이번에 맡은 것 |
|---|---|---|
| KISA 보호나라 | 제품 단위 한글 권고(Node.js 본체, MongoDB, MS 등) | Node.js 런타임 |
| CVE.org | 모든 CVE 번호, 공개 즉시 | PostgreSQL·nodemailer 등 새 건 |
| OSV.dev(GitHub 보안 권고) | 오픈소스 라이브러리 버전별 취약점 | 이미 쌓인 미패치분 전수 조회 |
- 📄 KISA 게시판에서 undici·multer·axios·lodash 등 npm 라이브러리 이름을 검색하면 0건이다. 🧠 "KISA 공지가 없다 = 안전"이 아니다. 라이브러리는 OSV나 `npm audit`으로 따로 봐야 한다.
- 📄 CVE.org 수집은 "앞으로 새로 나오는 것", OSV 조회는 "지금 쓰는 버전에 이미 알려진 것"을 본다. 등급은 CVE를 발급한 곳(예: OpenJS 재단)이 매긴 CVSS를 GitHub·OSV가 그대로 쓴다.

## 3. 조치 — 내 프로젝트 5곳 📄
저장소별로 하위 에이전트를 나눠 병렬로 진행했고, 머지·운영 배포는 사용자 확인 뒤 진행했다.

| 대상 | 바꾼 것 | 검증 | 결과 |
|---|---|---|---|
| 개인 허브 서비스 | Node 22.23.4→22.23.5, PostgreSQL 17.11→17.12, nodemailer 10.2.1→10.4.1 | 테스트 1,236건 + 실DB 테스트 90건(17.12 컨테이너) + CI 5종 통과 | 머지·외부판 배포 성공 |
| 메일 발송 앱 2개(배포 플랫폼) | nodemailer 6→10 메이저 상향, 엣지 함수 쪽도 10.4.1 | 테스트 215건·65건 통과, 무발송 스모크 테스트 | 머지. 1개는 배포 성공, 1개는 ⚠ 배포 연동 끊김 발견 |
| 협업 저장소 | Node 24.22.1→24.22.3(`.nvmrc`·engines·검사 스크립트·CI 이미지·컨테이너 파일) | 테스트 6,900건, 실패는 변경 전과 동일(새 실패 0) | 작업 브랜치 push |
| 개인 백오피스 | Docker 베이스 node:23(지원 종료)→node:24.22.3-alpine | 새 이미지에서 백엔드 설치·모듈 로드 확인 | 커밋 |
| 로컬 맥 | 기본 Node 24.22.3(공식 배포본 SHA-256 대조), Homebrew 26.13.1 | `node -v` | 완료 |

- 📄 **nodemailer 6→10 판단 근거**: 7(SES 전송 제거), 8(오류 코드 이름 변경), 9(원격 콘텐츠 TLS 기본 검증), 10(Node 20+·TypeScript 이전)을 확인했다. 사용 코드가 SMTP만 쓰고 오류 코드를 참조하지 않고 URL 첨부가 없어 **코드 수정 없이** 올라갔다. CVE 형태의 주소(`x@good.com (c) @evil.com`)가 `x@good.com`으로만 파싱되는 것도 확인했다.
- 📄 **이미지 digest 고정**: 협업 저장소는 CI 이미지를 multiarch index digest로 고정한다. 레지스트리 API로 실제 digest를 조회해 넣었다. 🧠 10월에 넣은 값은 같은 방법으로 조회한 값과 달랐다(플랫폼별 manifest였거나 태그 재빌드 가능성). 추측으로 digest를 쓰지 않는다.
- 📄 **DB 마이너 업그레이드**(17.11→17.12): 데이터 변환 없이 이미지 교체로 끝나는 범위. 교체 전에 백업 CronJob을 수동 실행해 최신 백업을 남기는 절차로 정리했다. 사내 클러스터 쓰기는 조회 전용 권한만 있어 사용자 실행으로 넘겼다.

## 4. 사내 제품 의존성 전수 점검 📄
- 제품 관리 화면에 공개된 서비스별 오픈소스 목록에서 22개 서비스, 고유 npm 패키지 1,649개를 브라우저 자동화로 수집했다.
- OSV.dev 대조: 취약 패키지 118개·204건, 치명·높음 68개. 치명 5종(IP 위조, 압축 해제 DoS, XSS 정화 우회, 템플릿 코드 주입, 웹소켓 메시지 변조).
- 🧠 **핵심 관찰**: 서비스 대부분이 같은 웹 서버 스택을 공유해, 요청 본문·업로드·HTTP 클라이언트·파서 계열 공통 라이브러리 6종이 18~19개 서비스에 동시에 들어 있었다. 서비스×패키지로 펼치면 약 200줄이지만 실제로 올릴 패키지 종류는 30여 개다. 공통 의존성 6종만 올려도 대부분이 정리된다.
- 📄 등록일 분포: 대부분 6~10월 공개분. 🧠 새로 터진 문제가 아니라 **업데이트가 밀려 쌓인 양**이다.
- 📄 CISA KEV(실제 악용 목록)와 대조해 해당 0건을 확인했다. 담당팀 사정으로 조치는 보류됐다. 🧠 보류 중 가장 현실적인 위험(인증 없는 DoS)은 ingress에서 요청 본문 크기·요청 수 제한, 압축 요청 차단으로 코드 없이 줄일 수 있다고 정리해 두었다.
- 전달물: 오픈소스 기준 표(현재·올릴 버전, 등급, 한국어 설명, 대상 서비스, 등록일, 출처)와 자료 출처·등급 기준 설명을 담은 단일 HTML 문서.

## 5. 아직 남은 것 (2026-11-16 기준)
- 사내 허브 DB 이미지 교체(postgres:17.12)와 사내 앱 릴리스 — 사용자 실행 대기.
- 메일 발송 앱 1개: 배포 플랫폼의 Git 자동 배포가 66일째 멈춰 있어 머지가 운영에 반영되지 않았다. 계속 쓰는지 확인 후 수동 배포 여부 결정.
- 메일 앱 2개의 엣지 함수 별도 배포.
- 고객 전달 샘플의 권장 Node 버전 안내, 서버리스 런타임 버전 확인.

## 6. 배운 점
- 📄 정확한 버전 고정은 **한 번 패치하면 끝나는 게 아니라 다음 릴리스에서 다시 걸린다**(10월 24.22.1 → 11월 재조치). 고정 위치 목록(10월 커밋)을 남겨 둔 덕에 이번엔 같은 절차를 그대로 재사용했다.
- 🧠 "공지가 없다"와 "취약점이 없다"는 다르다. 런타임·DB는 KISA·CVE.org로, 라이브러리는 OSV·`npm audit`으로, 두 갈래를 다 봐야 빈틈이 없다.
- 🧠 머지가 배포라고 믿으면 안 된다. 배포 연동이 끊긴 프로젝트는 머지해도 운영이 그대로다 — 머지 후 실제 배포 상태까지 확인하는 게 조치의 끝이다.
- 🧠 CVSS 등급은 "최악의 경우"다. 빌드 전용 도구의 높음과 외부 요청을 직접 받는 패키지의 높음은 실제 위험이 다르다. 전달 문서에는 등급과 함께 "어떤 조건에서 위험한지"를 적는다.
