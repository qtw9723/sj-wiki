> 당장 쓸 것 3가지: ① **dynamic workflows**(대규모 일괄 작업) ② **`/goal`**(조건 충족까지 자동 반복) ③ **routines/`/schedule`·`/loop`**(주기 실행). 기능 출처·주차는 [[Claude-Code-업데이트-동향]].

## "자동화의 마지막 단계 = 알림"
- 네가 [[schedule-reporter-kakao]]에서 카카오로 결과를 밀어주듯, Claude Code도 **mobile push notifications(W16)**, **terminalSequence 알림 훅(W20)**을 제공.
- 공통 원리: *수집 → 처리 → 사람에게 전달*. 자동화 설계 시 "어디로 알릴지"를 항상 마지막에 설계할 것.

## 에이전트 설계로 확장
- [[CogInsight-Generator]]가 "자연어→Dialog JSON" LLM 도구로 커지면, 이는 곧 **에이전트/툴 정의** 문제가 된다 → [[claude-api]](tool use, 구조화 출력, MCP) 참고가 필요해지는 지점.
- zod([[공통-기술스택]])로 LLM 출력 검증 = 에이전트 신뢰성 확보의 정석.

**🚨 확정된 결함 — 한국어 수집과 자동 위키화가 매일 같은 20분 창에서 경합한다**

- 📄 `.wiki-sync.sh` 구조: **line 75 `git_pull_rebase`(시작)** → 위키화 → **line 131 `git_pull_rebase`(push 직전)**.
- 🧠 세션이 보는 `raw/` 목록은 **line 75 pull(≈09:00~09:05)에 고정**되고, 한국어 파일은 그 뒤 **09:12~09:20**에 도착한다. line 131 재-pull은 파일을 받아오지만 **본문은 이미 다 써진 뒤**다.
- 🚨 📄 **실제 오탐**: 8/12 위키화가 *"한국어 파일 없음"* 이라고 기록했는데, 파일 커밋은 **09:14:03**, 그 판정 커밋은 **09:22:45**였다(8분 43초 늦게 커밋되며 이미 거짓이 된 판정을 기록).
- ⚠ 🧠 **3주간 안 드러난 이유는 이중화다**: 위 표의 **2차 경로(10:1x)** 가 매일 한국어 파일을 주워 처리해 왔다. **이중화가 단일 경로의 결함을 은폐**한 전형이다.

### 🚨 ⭐ 2026-08-16 갱신 — **`.wiki-sync.log`(1차 사료)를 처음 읽었다. 「1차 경로 중단」은 오판이었다**

> 🧠 위 절까지는 **커밋 타임스탬프로 실행 여부를 추론**한 결과다. 📄 그런데 `.wiki-sync.sh` line 20이 정의하는 **`$WIKI/.wiki-sync.log`** 에 실행·건너뜀·에러가 시각과 함께 전부 남아 있었고, 3주간 아무도 열지 않았다.

📄 **실행 로그 실측 (KST)**

| 시각 | 로그 | 커밋 | 실제 |
|---|---|---|---|
| 8/13 18:00:06 | `변경 없음 — 건너뜀` | 없음 | ✅ 기동 |
| 8/14 09:00:06 | `변경 없음 — 건너뜀` | 없음 | ✅ 기동 |
| 8/14 18:00:05 | `감지` → `위키화 완료` → `✅ git push 완료` | `dede7a1` (+0900) | ✅ **성공** |
| 8/15 09:00:04 | `변경 없음 — 건너뜀` | 없음 | ✅ 기동 |
| 8/15 18:04:16 | `감지` → 18:48:20 **`ERROR: claude 실행 실패`** (`API Error: Connection closed mid-response`) | 없음 | 🚨 **실패** |
| 8/16 09:00:07 | `감지` | (13차 보강) | ✅ 기동 |

- 🚨 📄 **6회 전부 기동했다 — 「중단」은 없었다.** 커밋 0건의 원인은 셋(파일 미도착 / claude 실행 실패 / **판정 세션 자신의 커밋**)인데 판정은 하나였다.
- ✅ 📄 **09:00 경합 진단은 오히려 강화됐다**: 09:00 슬롯은 매번 `변경 없음 — 건너뜀`이다. 📄 `naver-2026-08-15.md`의 **로컬 mtime = 8/15 18:04**(원격 수집 커밋은 09:11 KST) → `find raw -newer $MARKER`(line 81)는 **pull이 내려받은 시각**을 보므로 09:00 패스엔 파일이 **존재조차 하지 않는다**. 🧠 실제 구조는 *"09:00은 매일 헛돌고 **18:00이 주워담는다**"*.
- ✅ 📄 **2차 경로(`+0000`, 10:1x) 후보 하나 제외**: `.wiki-sync.log`에 **10:1x 항목이 한 줄도 없다** → 🧠 **이 맥의 `.wiki-sync.sh`가 아니다**(다른 호스트/클라우드 실행). 주체는 여전히 불명.
- ✅ 📄 **마커 자가 수렴은 설계대로 동작한다**: §6은 **push 성공 시에만 `touch $MARKER`** 한다. 8/15 실패로 `.last_wiki_sync`가 **8/14 18:10에 정지** → 8/16 패스에 같은 파일이 재투입 → 감사 기회가 생겼다.
- ⭐ 🧠 **세션 신분 판별은 이미 가능했다**: 📄 로그 마지막 `신규/변경 파일 감지` 줄이 **그 세션의 대상 파일·시각과 일치**하면 launchd 자동 패스다. → `[출처: AUTO/launchd]` 마커(아래 처방 3의 후속)는 **편의 개선이지 차단 요인이 아니다**.
- 🧠 **일반화(규약 후보, 사람 확인 대기)**: *실행 여부는 **프로세스 자신의 로그**로 판정한다. 커밋·파일 등 산출물은 2차 사료이며, **산출물을 내지 않는 정상 실행**과 실패를 구분하지 못한다.* → [[웹-크롤링-기초]]

**✅ 처방 (실행 대기)**

1. plist 09:00 슬롯 `<key>Minute</key><integer>0</integer>` → **`30`**. 📄 관측 도착 범위(09:12~09:20)보다 항상 뒤. 여유를 더 두려면 09:45.
2. `.wiki-sync.sh`에 **같은 날짜 한국어 파일 부재 시 재-pull → 재확인** 분기를 **위키화 전에** 추가.
3. 위키화 프롬프트: *"부재는 재-pull 뒤 재확인한 결과만 기록. 확인 안 했으면 「없음」이 아니라 **「미확인」**"*.
4. ⚠ **2차 경로의 정체 확인** — 무엇이 10:1x에 도는지 모르는 상태로 1차를 고치면, 고쳤는지 확인할 방법이 없다.
5. 📄 **미해결 질문(코드 확인 필요)**: ai-crawler에 **소스별 `max_items` 파라미터가 있는가?** 🧠 있으면 롤링 만료는 크롤러 설정, 없으면 **업스트림 RSS가 노출하는 항목 수**다. 📄 「OpenAI 상한 15」 가설은 8/13에 반증됐다(15+2=17, 만료 0) → [[웹-크롤링-기초]] ③-g.

## 의외의 연결점
- 🆕 🚨 **"자동화가 조용히 틀리는 것"을 잡는 데 필요한 건 도구가 아니라 「단계 특정」이다**([[AI-주간-소식-2026-W33]] (W33-EN27) ASCon): 📄 실패 귀속에는 *누가 · **언제(어느 단계)** · 왜* 가 필요한데, 🧠 [[웹-크롤링-기초]]의 실패 19종은 3주간 **「실패 모드」만 적고 「단계」를 안 적었다** — 그래서 매번 *"하네스 수정 TODO(미적용)"* 로 끝났다. 위 절이 그 결함을 처음 메운 사례다.
- **SM 시절의 크론·네트워크 운영 감각([[내-프로필]])**이 여기서 빛난다: 스케줄링·모니터링·알림은 SM 업무의 본질이었고, 지금 도구만 AI로 바뀐 것. 너는 자동화 전환에 이미 직관이 있다.
- **회사 업무에도 같은 패턴**: 본업의 "정해진 시각 자동 발송·상태 판정" 류 작업도 전형적 크론/모니터 → routines·`/schedule`·Monitor와 동형. 자동화 설계 직관이 그대로 전이.
- **MCP 커넥터 환경**: 네가 실제 쓰는 scheduled-tasks·computer-use 등은 [[내-MCP-커넥터-환경]] 참고.
