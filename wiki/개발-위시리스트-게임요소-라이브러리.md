> [!tip] 핵심 takeaway
> 📄 사용자 구상(2026-10-21): 게임 하나를 파서 복제하지 않고, **여러 게임의 좋은 요소를 분석해 위키에 쌓은 뒤 이를 조합해 완전히 새로운 게임**을 만든다. 상태 🟡 **진행예정(나중에 착수)**.
> 🧠 위키 취지(한 번 정리해 쌓고 계속 재사용)와 같은 구조이고, Cogi 시나리오 레퍼런스(카테고리별 자료를 쌓아 조립)와 같은 패턴이라 익숙하다. 첫 적용처는 [[개발-위시리스트-메이플스토리|몬스터북 사가]]·[[게임-프로젝트-MonsterCollector-MonsterRank]] 같은 내 게임.

## 1. 배경 — 왜 "한 게임 복제"가 아니라 "요소 라이브러리"인가 (🧠 판단)
| 비교 | 한 게임 분석 → 비슷한 게임 | 여러 게임 요소 → 새 게임 |
|---|---|---|
| 법적 리스크 | 높음(EULA 역공학 금지, 복제 시비) | 낮음(규칙·메커니즘 같은 아이디어는 일반적으로 저작권 보호 대상 아님) |
| 토큰 | 매번 게임을 다시 팜 | 요소당 1회 분석 후 위키 재사용 |
| 결과물 | 아류작 | 새 조합 |
| [[REA-Reverse-Engineer-Anything|REA]] 필요성 | 높음 | 낮음(정확한 수치가 필요한 요소에만) |

## 2. 정보 수집 방법 (🧠 판단)
- 대부분은 **역공학 불필요**: 직접 플레이 경험, 공략 위키, 개발자 강연(GDC 등), 패치노트.
- **REA는 정확한 숫자가 꼭 필요할 때만**: 데미지 공식, 물리 상수, 드롭 확률 등. 📄 REA는 Unity IL2CPP·Godot PCK·네이티브·WASM을 지원하고, 쇼케이스(DX-Ball 사운드 팬, TH04 탄막 계산)도 게임 메커니즘 1개를 정확히 복원하는 형태.
- 그냥 "비슷한 게임"을 만들 거면 플레이하며 규칙을 설명하는 것만으로 충분.

## 3. 위키 구조 설계 (🧠 제안, 착수 시 적용)
> [!warning] 구버전 초안 → 정본은 [[게임요소-라이브러리]] (2026-10-21 규약·검색 시스템 확정). 아래는 최초 초안 기록용.

- **요소(메커니즘) 단위 페이지**, 게임 단위 아님. 파일명 `게임요소-<이름>.md` (예: `게임요소-로그라이크-런-구조`, `게임요소-수집-도감-보상`). 위키 규칙대로 폴더 없이 플랫, index에 **"게임 요소" 카테고리 신설**.
- **요소 페이지 템플릿**
  ```markdown
  ---
  title: 게임요소 — <이름>
  category: 게임 요소
  tags: [장르:<>, 경험:<성취/긴장/수집/...>, 난이도:<하/중/상>]
  source: <게임·공략·강연 URL>
  ---
  > [!tip] 핵심 takeaway
  ## 핵심 규칙        — 한 줄 정의 + 동작 방식
  ## 출처 게임들      — 잘 쓴 게임과 각 게임의 변형
  ## 왜 재밌나        — 플레이어 경험(성취감·긴장·수집욕 등)
  ## 수치             — 📄 실측·공식 자료 / 🧠 추정 구분
  ## 조합 궁합        — 잘 맞는 요소 / 충돌하는 요소
  ## 구현 메모        — 난이도, MSW(Lua) 구현 포인트([[MSW-개발-레퍼런스]])
  ## 관련 문서
- [[게임요소-라이브러리]] — ⭐ 규약·검색 시스템 정본
  ```
- **조합 실험 페이지** `게임요소-조합-실험.md`: "요소 A + B + C → 새 게임 아이디어"를 기록하고, 만들어 본 결과(재미 여부·막힌 곳)를 회고로 남김 → 위키가 점점 똑똑해짐.

## 4. 주의 (🧠)
- 요소가 수십 개로 늘면 index만으로 고르기 어려움 → **처음부터 태그(장르·경험 유형·구현 난이도)를 일관되게**.
- 수치는 출처가 섞이기 쉬움 → **📄 실측 / 🧠 추정 표기 필수**.
- 에셋(그래픽·사운드)은 저작권 대상 → 규칙·메커니즘만 참고, 에셋은 새로 제작.
- **온라인·멀티플레이 게임은 역공학 금지**(안티치트 계정 정지·법적 문제).
- 모드가 목적이면 공식 모딩 툴/SDK 있는 게임 우선. MSW처럼 공식 제작 플랫폼이면 역공학 자체 불필요.

## 5. 토큰 대략치 (🧠 추정, 실측 아님 — 2026-10-21 대화)
| 작업 | 누적 토큰(입력+출력) | 비고 |
|---|---|---|
| 규칙 설명만으로 간단한 게임 제작(역공학 없음) | 5만~20만 | 가장 쌈 |
| 웹/HTML5 게임 구조 파악 + 비슷한 게임 제작 | 10만~30만 | JS 번들의 필요한 부분만 |
| Unity/Godot 인디 게임 메커니즘 1개 분석 | 20만~100만 | 메타데이터 덤프가 커서 범위 좁히기 |
| 네이티브 게임 전체 분석 | 수백만 이상 | 비현실적, 메커니즘 단위로 분할 |

- 에이전트는 매 턴 컨텍스트를 다시 읽어 **누적 입력이 비용 대부분**, 캐시 적용 시 크게 감소.
- 절약: 메커니즘 하나씩 세션 분리("점프 물리만"), 분석 결과는 **요약본만** 다음 단계로.
- Claude Code 구독은 달러가 아니라 사용량 한도 소모. 정확한 값은 작은 게임 1개로 시범 후 `/cost`·`/usage`로 실측.

## 6. 착수 시 첫 단계 (🧠 제안)
1. ✅ 규약·검색 시스템 확정 → [[게임요소-라이브러리]] (2026-10-21).
2. 내 게임과 관련 있는 요소 1개(예: **수집 도감 보상**)를 첫 샘플로 작성.
3. 요소 3~5개 쌓이면 `게임요소-조합-실험`에 첫 조합 기록 → 작은 프로토타입으로 검증·토큰 실측.
