> [!tip] 핵심 takeaway
> 🧠 배포 전략의 요체: **카톡을 이기려 하지 말고 카톡을 통로로 쓴다.** 팀장이 세트 링크를 기존처럼 단톡방에 던지면 되므로 팀원의 습관이 그대로다 → 전환 마찰 거의 0.
> ⚠️ 🧠 **가장 큰 실무 함정은 카카오톡 인앱 브라우저**다. 이거 빠뜨리면 "왜 자꾸 로그인하래?"라는 불만이 바로 나온다.

## 1. 배포 흐름 (📄 D8 + 5차 사용 흐름)

```
팀장: 세트 구성 → 링크 생성 (share_token)
  → 카카오톡 단톡방에 링크 공유    ← 기존 습관 그대로
팀원: 링크 탭 → 웹 열람 · 메모
앱 설치 후: 링크가 앱으로 열림 (딥링크, 추후)
```

- 📄 "그냥 웹페이지에서도 접근 가능하게" — 링크 없이 직접 방문해 지난 곡목·전체 아카이브를 볼 수 있는 경로도 함께 제공.
- 📄 D3 "꼭 하나의 PDF일 필요는 없다" → 앱 안에서는 **곡 단위로 넘기는 뷰어**가 기본. 병합 PDF는 **다운로드 옵션**으로만 남긴다(인쇄·오프라인 백업용).

## 2. ⚠️ 카카오톡 인앱 브라우저 (🧠 최우선 검토 항목)

📄 현재 팀은 카톡으로 PDF를 공유 중 → 링크도 당연히 단톡방에 올라가고, 팀원은 **카톡 안의 브라우저**로 연다. 한국 서비스에서 자주 사고 나는 지점이다.

| 문제 | 영향 |
|---|---|
| 인앱 브라우저는 크롬/사파리와 **저장소가 분리**됨 | 여기서 로그인해도 나중에 사파리로 열면 로그아웃 상태 → 반복 로그인 불만 |
| **홈 화면에 추가(PWA 설치)가 안 됨** | 앱처럼 쓰는 경로가 막힘 |
| 오프라인 캐싱이 기대대로 동작하지 않음 | 📄 D7 요구사항이 무력화됨 |

**대응 (🧠 필수 구현)**
- 링크 진입 시 인앱 브라우저를 감지해 **"기본 브라우저로 열기" 안내**를 띄운다.
  - Android: `intent://` 스킴으로 크롬을 직접 실행 가능
  - iOS: 직접 실행이 막혀 있어 **안내 배너로 유도**(우측 상단 메뉴 → Safari로 열기)
- 🧠 작은 디테일 같지만, 이게 없으면 **인증 설계 전체가 체감상 실패**한다 → [[악보-아카이브-인증-권한]] §5 체크리스트에도 등재.

## 3. PWA 검토 (📄 D8 "웹 기반의 모바일 앱 배포")

**장점 (🧠)**: 설치 없이 링크로 열림 / 홈 화면 추가 시 앱처럼 동작 / 업데이트 배포 즉시 / 코드 하나로 iOS·Android·PC 커버 — 2인 개발에 가장 현실적.

**확인해야 할 제약 (🧠)**

| 항목 | 상태 | 비고 |
|---|---|---|
| 애플펜슬 필기 | ⚠️ **선행 검증 필요** | iPad Safari는 Pointer Events로 필압·기울기 지원. 다만 네이티브 앱 대비 **지연(latency)** 체감 차이 가능 |
| 오프라인 저장 용량 | ⚠️ 제한 있음 | iOS Safari는 저장 공간을 제한하고 미사용 시 정리 가능 → "이번 주 세트만 캐싱" 전략 |
| 홈 화면 추가 | ✅ 가능 | 단, 인앱 브라우저에서는 불가 (§2) |
| 푸시 알림 | △ | iOS는 홈 화면 추가한 PWA에서만. 곡목 배포 알림을 푸시로 할지 카톡으로 할지 결정 필요 |

> [!danger] 🧠 프로젝트 성패를 가르는 단일 검증 항목
> **iPad Safari 펜슬 필기 프로토타입을 개발 초기에 만들어 볼 것.** 문서상으로는 판단이 불가능하고, 이 결과가 "PWA로 끝낼지 / 네이티브 껍데기를 씌울지"를 결정한다. 나중에 발견하면 되돌리는 비용이 크다.

**대안 경로 (🧠)**: PWA 필기가 만족스럽지 않으면 → **Capacitor로 감싸 네이티브 껍데기만** 씌운다. 웹 코드는 그대로 재사용되고, 인앱 브라우저 문제와 저장 제약이 동시에 해소된다. 🧠 앱화의 가장 큰 실익이 사실 이 두 가지다.

## 4. 뷰어 요구사항 (📄 요구 8 "실전에서 악보 뷰어로서의 기능")

🧠 실전(예배 중)이라는 조건이 붙으면 일반 PDF 뷰어와 요구가 달라진다:

- [ ] **큰 탭 영역으로 페이지 넘김** — 예배 중 정확한 탭이 어렵다. 화면 좌우 절반을 넘김 영역으로
- [ ] **곡 간 이동** — 세트 안에서 다음 곡으로 바로 (곡 목록 드로어)
- [ ] **화면 꺼짐 방지** (Wake Lock) — ⚠️ 🧠 없으면 예배 중 화면이 꺼진다. 놓치기 쉬운 필수 항목
- [ ] **다크/조명 모드** — 어두운 예배당에서 흰 배경은 눈부시다. 반전 또는 밝기 조절
- [ ] 확대/이동, 두 페이지 보기(가로 모드)
- [ ] 메모 레이어 on/off → [[악보-아카이브-메모-동기화]] §2
- [ ] 송폼 바 (추후: 탭하면 해당 마디로 점프) → [[악보-아카이브-데이터-모델]] §3
- [ ] 세트 전곡 선제 캐싱(prefetch) 상태 표시 — "오프라인 준비 완료" 표시가 있으면 팀원이 안심한다

## 5. 카톡 대비 차별점 (🧠 — 왜 이걸 써야 하는가)

📄 현재 방식이 카톡 PDF 공유이므로, **카톡이 못 하는 것**이 이 서비스의 존재 이유다.

| 카톡이 못 하는 것 | 이 서비스 |
|---|---|
| 지난 곡목 검색 (스크롤 지옥) | 날짜·곡 기준 조회, "이 곡 마지막으로 언제?" |
| 매번 새 파일 → 필기가 안 남음 | 곡에 붙는 메모가 계속 따라옴 (D1) |
| 가사·키로 곡 찾기 불가 | 다축 검색 (D5) |
| 곡별 키·송폼 관리 없음 | 메타데이터 + 공용 메모 |

🧠 반대로 **배포 자체는 카톡을 이기려 하지 않는다** — 링크를 단톡방에 던지는 방식을 그대로 둔다. 링크만 눌러본 사람도 자연스럽게 서비스로 유입된다.
