> [!tip] 핵심 takeaway (포트폴리오 관점)
> ⭐ **"delivery팀용 챗봇 모니터링 허브"로 시작해 3개월 만에 "코드 1·DB 1·모듈 N·허브 N" 통합 플랫폼이 됐고, [[mailer|CS SmartHub]]를 완전히 흡수(컷오버→구 앱 은퇴→구 테이블 폐기)했다.** 팔 포인트는 기능 수가 아니라 **(1) 모듈 레지스트리 + `hub_features` 매트릭스 + 허브=URL 구조로 팀·기능 확장이 "행 추가"가 되게 한 설계, (2) 라이브 서비스를 끊지 않고 단계적으로 옮기고(공유 테이블+`hub_id`→컷오버→폐기, 되돌릴 백업 보존) (3) 운영하면서 "측정할 칸"을 먼저 만들고 그 데이터로 자기 해석을 뒤집은 운영 성숙도**다.
> 🧠 **2026-11-10부터 같은 코드가 두 에디션으로 돈다** — 외부(Vercel·Supabase: 개인 MVP·포트폴리오·사내망 밖 직원)와 사내(회사 k8s·자체 Postgres: 회사 정식 버전, 사내망 전용). API는 같고 DB 접근 코드만 에디션별이다. 허브 2개(cs·delivery)·모듈 6종이 돌고, Grafana AI 일일 리포트는 사내 서버에서 발송된다. 포트폴리오로는 "만들었다"보다 **"운영하며 고쳐 온 기록 + 하나의 코드로 두 운영 형상을 유지하는 설계"** 가 강점.
> ⚠️ 불변 원칙: DB 변경은 Management API 멱등 SQL만(`supabase db push` 금지 — [[mailer]]와 동일), 새 테이블 RLS 필수([[Supabase-RLS-정책]]).

## 한 줄 소개
**여러 팀의 업무 자동화를 담는 통합 플랫폼.** 기능은 **모듈**, 팀은 **허브**(`/hub/:hubKey` 링크), 전체는 **백오피스**(`/admin`)가 관망한다. 코드 하나·Supabase 하나로 운영하고 데이터는 `hub_id`로 스코프된다. 📄(README)

## 문제 / 배경
- 📄(사용자·2026-07-21 세션) [[mailer|CS SmartHub]]가 CS팀 자동화 허브로 자리잡자 **delivery팀도 같은 방식의 도구**가 필요했고, 기능을 하나씩 붙이면서 **중간에서 전체를 관리할 백오피스**가 필요했다.
- 📄 이후 방향이 확장됐다: 팀마다 repo·DB를 복제하지 않고 **한 플랫폼에서 팀 허브·모듈 on/off**로 해결 → 기존 CS 앱(mailer)도 이쪽으로 이전(M1~M5 "mailer→SmartHub 완전 마이그레이션" 프로그램, 2026-07-22 설계).

## 내 역할
📄 기획·설계·구현·배포·운영 전부 본인(1인). 🧠 AI 페어(Claude Code)로 브레인스토밍→스펙→계획→TDD 흐름(`docs/superpowers/specs·plans`)을 쓰되, 결정(범위·삭제·정지 등)은 사용자가 내리고 파괴적 작업은 단계별 승인 후 실행.

## 3층 구조 (아키텍처) 📄(README)
```
SmartHub (코드 1 · DB 1)
├─ 모듈(기능): chatbot-monitoring · grafana-reports · mailer · doc-to-esd · doc-to-api · websdk-test(2026-10-28)
├─ 허브(팀): CS · Delivery · … (링크 /hub/:hubKey), hub_features(hub_id, feature_key)로 허브별 모듈 on/off
└─ 백오피스(/admin): 모듈 레지스트리 순회로 허브 × 모듈 관망
```
- **모듈 계약**: 운영 모듈 = {API 라우터 + 프론트 `HubPanel`/`SettingsPanel` + `hub_id` 테이블 + overview}. 무상태 툴 = {key + `HubPanel` 또는 `loadPanel`(지연 로드)} — 나머지는 옵셔널. 서버 파트가 없어도 서버 레지스트리에 `{ key }`로 등록(백오피스 토글·overview 기준).
- **확장 비용**: 팀 추가 = `hubs`+`hub_features` 행 / 모듈 추가 = 레지스트리에 계약 구현·등록.
- **프론트** React 19 + Vite 8 + Tailwind 4(다크 테마 토큰) · **API** Express(`/api/modules/<key>/*` · `/api/hubs/*` · `/api/admin/*`, 구 `/api/chatbot/*`는 크론용 alias) · **러너** Playwright(`HUB_KEY`로 허브 한정, GitHub Actions) · **DB** Supabase(mailer와 공유 프로젝트, [[parking]]) · **배포** Vercel(main 머지 = 자동 배포 = 릴리스) · **LLM** Gemini(Grafana 일일 분석).
- **테스트/CI**: vitest·supertest(테스트 파일 68개, v0.9.0 시점 771 통과), `ci.yml`(lint·테스트·빌드), `cogi-drift.yml`(매일 상류 감시), 정기 워크플로우 실패 시 메일 알림(v0.11.0).
- **데이터**: `hubs`(비밀번호 scrypt 해시) · `hub_features` · `hub_chatbots`/`hub_chatbot_check_log`/`hub_chatbot_settings` · `hub_module_calls`(호출 상한) · 공유 테이블에 `hub_id` 스코프(grafana_report_settings·grafana_log_types·mail_jobs·sender_accounts 등) · `grafana_sources`(환경별 멀티소스). 마이그레이션 17개(`supabase/migrations`).

## 운영 중 배운 것 (포트폴리오 STAR 소재) 🧠
- **"측정할 칸"을 먼저 만든다**: 재시도가 몇 건을 살렸는지·로그 유형이 id로 붙는지 답할 데이터가 없어 `attempts`·`matched_by`를 심었고, 3주 뒤 그 데이터가 가설 둘을 판정했다(챗봇 재시도 구제 0건 → 10-14 즉시 재시도 끔).
- **자기 해석을 데이터로 뒤집는다**: "매일 깨진 챗봇 3개"가 분모를 안 본 오기였고, 미래에셋 20일 연속 실패는 챗봇이 아니라 **점검 키워드가 낡은 것**이었다(10-26 규명·재개) — 응답 발췌만 보고 판정하지 말 것.
- **장애 증폭 구조 제거**: 429를 재시도하던 코드가 호출 1회를 최대 4건으로 키워 Gemini 일일 한도를 소진 → 서버가 알려준 대기 시간을 따르게 수정(v0.10.0). 10-26 07시 메일 누락은 분석 마감 40초 + 따라잡기 발송으로 보강.
- **"조용한 스킵 = 실패"**: 이식 가드·감시가 조용히 비어 있던 사례를 반복 발견(감시 경로 5개가 처음부터 상류에 없었음, 알람이 2주 빨간 줄 아무도 몰랐음) → 존재 확인·메일 알림으로 구조적으로 막음.
- **파괴적 작업의 순서**: 구 앱 정리는 백업 대조 가드(행수 다르면 중단)·FK 자식부터·`CASCADE` 없이·복구 경로 문서화·단계별 승인.
- **코드 하나·형상 둘**(11-09~10): 처음 설계는 "두 에디션 모두 같은 Postgres 드라이버"였으나 사용자가 "API 이름은 같게, 서버별 백엔드 코드만 다르게"로 바로잡아 저장소 계층(외부 supabase-js 그대로·사내 pg) + 같은 시나리오를 두 경로로 돌리는 **계약 테스트**로 갔다 — 외부 운영을 건드리지 않고 사내를 세운 핵심.
- **옮길 때는 "두 번 보내지 않기"부터**: 메일·알림처럼 밖으로 나가는 것은 꺼진 채 복사하고, 넘길 때 사내를 켜고 외부를 끈다. Grafana는 LLM이 쌓은 로그 유형까지 관계를 유지해 옮기고 마지막 발송일을 맞춰 전환 당일 중복을 막았다.
- **내리기 전에 대조표**: 단독 앱을 정리하다 문서 탭이 빠졌다 — 예전 "원본에서 본다" 결정의 전제가 정리로 깨진 것(사용자가 공지 직전 발견). 이후 규칙: 원본을 내리기 전 기능 대조표.
- **환경이 바꾸는 버그**: 사내망 http에서는 브라우저가 `crypto.randomUUID`·클립보드 API를 주지 않아 설정 화면이 멈췄다 — https였던 외부에선 절대 안 보이던 종류. 대체 구현 + 직접 호출 금지 테스트.
- **설정 대신 관측값으로 진단한다**(11-12): 외부판이 느렸던 원인은 함수(미국 동부)와 DB(도쿄)의 리전 불일치였다. API 권한이 막혀도 응답 헤더 `x-vercel-id`로 실제 실행 리전을 확인했고, `regions: ["hnd1"]` 한 줄로 DB 1회 조회 API p50 891ms → 137ms(-85%). DB 없는 엔드포인트를 대조군으로 함께 쟀다 → [[SmartHub-API-지연-개선-리전-정렬]].
- **보안은 공지 유형으로 읽는다**: 남의 제품 공지(비밀번호 무차별 대입)가 우리 구조(시도 제한 없음)에 그대로 해당 → 잠긴 동안 맞는 값도 거절하는 시도 제한. 서버리스라 카운터는 DB에.

## 이력: Phase1(2026-07-21) 설계 — 압축 📄

## 불변 원칙 (갱신)
- DB는 Management API 멱등 SQL만(`supabase db push` 금지 — [[mailer]] 규칙과 동일, 공유 Supabase에 원격 전용 마이그레이션이 있어 divergence). 새 테이블은 RLS 필수.
- 구 cs 테이블(`chatbots`/`chatbot_check_log`/`chatbot_monitor_settings`)은 런타임에 읽거나 쓴 적 없고 2026-09-14 폐기됨(백업으로 복원 가능). cs 키·시크릿은 전량 보존.
- Cogi 상류는 수동 동기화 — Cogi Tailwind 테마는 가져오지 않고 SmartHub 토큰으로 변환해 이식.
- (11-10) 사내·외부 DB는 각자 관리 — 마이그레이션은 `db/migrations/{common,external}` 한 벌을 두 DB에 각자 적용. 사내 서버 명령(kubectl·Secret)·DB 쓰기는 사용자가 실행, 회사 깃 `deploy` 병합 = 운영 배포라 요청 시에만.
- (11-10) 작업마다 문서(README·CHANGELOG·ROADMAP·운영 가이드·회사 깃 README)를 같은 PR에서 갱신.
