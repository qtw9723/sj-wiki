> [!tip] 핵심 takeaway
> 📄 찬양팀(20명 내외)이 **카톡 PDF 공유**로 하던 악보 배포를 대체하는 서비스. 팀장이 주일 곡목을 묶어 링크로 전달하면, 팀원은 웹/앱에서 악보를 보고 그 위에 메모한다.
> 🧠 이 프로젝트의 승부처는 성능이 아니라 **전환 마찰**이다 — 20명 규모라 인프라 고민은 사실상 없고, "카톡보다 편한가"만 남는다. 그래서 배포는 카톡을 이기려 하지 않고 **링크를 카톡에 던지는 방식 그대로** 간다.
> 🧠 기술적 난이도의 절반 이상이 **필기 메모 + 오프라인 동기화**에 몰려 있다 → MVP에서 빼고 스키마만 미리 열어둔다.

## 개요

| 항목 | 내용 |
|---|---|
| 목적 | 📄 찬양팀 악보 아카이브 + 예배별 곡목 구성·배포 + 실전 뷰어 |
| 사용자 | 📄 찬양팀 20명 내외 (추후 비슷한 규모 팀 여러 개 추가 가능 — 추후 고려) |
| 현재 방식 | 📄 카카오톡으로 PDF 공유 |
| 개발 | 📄 [[내-프로필\|박상준]] + 백은률, 2인 — 단 **프로토타입은 박상준 단독 개발 확률 높음** |
| 배포 형태 | 📄 우선 링크 배포 → 웹 기반 모바일 앱(PWA) 검토 중 |
| 저장소 | 📄 프로토타입=본인 Supabase(임시) / 운영=미정, AWS 유력 → [[악보-아카이브-데이터-모델]] §1-1 |

## 요구사항 (📄 사용자 구술 9개 골자)

1. 악보들의 아카이브화
2. 매번 선곡되어 짜여지는 예배 곡목에 대한 기록 및 메모 기록
3. 선곡된 곡목의 빠른 배포
4. 핸드폰(패드) 어플화
5. 악보별 메모 기록
6. 악보 검색의 다양성
7. 악보 저장은 NAS 혹은 클라우드, 웹/앱에서 불러 사용
8. 실전에서 악보 뷰어로서의 기능
9. 로그인 및 회원관리 / 부서별 관리

| D2 | 메모 레이어를 **공용/개인으로 분리** | [[악보-아카이브-메모-동기화]] |
| D3 | 곡모음이 **반드시 하나의 PDF일 필요는 없다** | [[악보-아카이브-뷰어-배포]] |
| D4 | **송폼은 자동 추출하지 않고 공용 메모로** 활용 | [[악보-아카이브-데이터-모델]] |
| D5 | 스캔은 **1단계(제목·작곡가·키) + 가사**만 검색에 활용, 나머지는 메모로 | [[악보-아카이브-데이터-모델]] |
| D6 | 원본은 각 형식 그대로 두되, **PDF가 아니면 PDF로 전환**해 저장 | [[악보-아카이브-데이터-모델]] |
| D7 | 오프라인 캐싱 지원하되 **작성 중이던 메모가 유실되면 안 된다** | [[악보-아카이브-메모-동기화]] |
| D8 | 배포는 **링크 우선**, 이후 웹 기반 앱 | [[악보-아카이브-뷰어-배포]] |
| D9 | 로그인은 **자동 로그인이 되면 이상적**, 링크 없이 웹 직접 접근도 지원 | [[악보-아카이브-인증-권한]] |

## 사용 흐름 (📄)

```
팀장: 곡목 구성 (악보 선택 → 순서 배치 → 세트 생성)
  ↓  링크 생성
  ↓  카카오톡 단톡방에 링크 공유   ← 기존 습관 그대로
팀원: 링크 탭 → 웹 접근
  ↓  (로그인 상태면 바로 곡목 화면)
  ↓  악보 확인 · 메모 작성
앱 전환 후: 앱에서 알아서 접근해 열람
```

## MVP 범위 (🧠 2인 개발 기준 제안 — 사용자 확정 필요)

| 넣을 것 (MVP) | 뒤로 미룰 것 |
|---|---|
| 악보 업로드 + PDF 정규화 | OCR 자동 메타데이터 |
| 곡 메타데이터 수동 입력 | 가사 검색 |
| 세트 구성 + 링크 공유 | 조옮김 |
| 뷰어 (페이지 넘김) | 오프라인 캐싱 |
| 로그인 / 팀 권한 (`team_id` 포함) | 멀티팀 UI |
| — | 펜슬 필기 메모 |

> [!warning] 🧠 MVP에서 필기·오프라인을 빼는 이유
> 이 둘이 전체 난이도의 절반 이상인데, 정작 MVP가 검증해야 할 질문은 **"팀원들이 카톡 대신 이 앱을 실제로 여는가"**다. 그건 필기 없이도 확인된다. 단, **스키마는 처음부터 스트로크 저장을 염두에 두고** 설계해 나중에 얹기 쉽게 한다 → [[악보-아카이브-데이터-모델]].

> [!note] 🧠 프로토타입은 단독 개발 — 범위를 더 줄인다
> 📄 프로토타입은 박상준 혼자 만들 확률이 높다. 2인 기준 MVP보다도 **더 얇게** 가는 게 맞다:
> - 로그인도 처음엔 생략하고 **하드코딩된 사용자 1명**으로 시작해도 된다 (인증 구조는 [[악보-아카이브-인증-권한]]에 정의만 해두고 구현은 나중에)
> - 악보 등록은 UI 없이 **Supabase 대시보드에서 직접 업로드**해도 검증에는 지장 없다
> - 검증 대상 2가지(링크를 여는가 · 펜슬이 쓸만한가)에 직접 기여하지 않는 것은 전부 뒤로 민다
> - 🧠 다만 **`team_id`와 `storage_path` 규약만은 프로토타입에서도 지킨다** — 나중에 소급 적용이 가장 아픈 두 가지다.

> [!danger] 🧠 반드시 선행 검증할 것 (프로토타입)
> **iPad Safari에서의 애플펜슬 필기 지연(latency)**. Pointer Events로 필압·기울기는 지원되지만, GoodNotes 같은 네이티브 앱에 익숙한 팀원에게 웹 필기가 만족스러울지는 문서로 판단이 불가능하다. 이 하나가 "PWA로 갈지 / 네이티브 껍데기(Capacitor)를 씌울지"를 가른다.

## 기술 스택 (🧠 초안, 미확정)

- 프론트: React 기반 웹 (PWA) — [[팀숲-bible-forest]]에서 쓴 Next.js 경험 재사용 가능
- 백엔드/DB: 📄 **프로토타입은 Supabase 신규 프로젝트**(⚠️ [[parking]] 공유 인스턴스에 얹지 않음). 운영 전환 시 AWS(RDS+S3+Cognito) 유력 → 락인 회피 3규칙은 [[악보-아카이브-데이터-모델]] §1-2
- 파일 저장: 📄 프로토타입 Supabase Storage → 운영 시 S3 (S3 호환이라 경로 규칙 유지)
- PDF 렌더링: PDF.js 계열
- 조옮김(먼 로드맵): 📄 이전 검토안 = React + OpenSheetMusicDisplay / FastAPI + music21 / Claude API OMR

## 로드맵 (🧠)

| 단계 | 내용 |
|---|---|
| **Phase 0 (프로토타입)** | 📄 **박상준 단독.** Supabase 신규 프로젝트에 최소 스키마 + 업로드 + 뷰어 + 세트 링크. 🧠 목적은 기능 완성이 아니라 **두 가지 검증** — ① 팀원이 카톡 대신 이 링크를 여는가 ② iPad 펜슬 필기가 쓸만한가 |
| Phase 1 (MVP) | 업로드·정규화 / 곡 CRUD / 세트 구성 / 링크 배포 / 뷰어 / 로그인·팀 |
| Phase 2 | 개인·공용 메모(필기 + 타이핑), 오프라인 캐싱 + 동기화 |
