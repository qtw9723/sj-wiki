> [!tip] 핵심 takeaway
> 🧠 sj-wiki RAG(`rag/`)는 BM25로 단어가 맞는 청크를, 임베딩으로 뜻이 맞는 청크를 따로 찾고 두 순위를 RRF로 합친다. 두 검색기가 틀리는 지점이 달라서 섞는다. BM25 단독은 한국어 질의 hit@1 1.00, 영어·동의어 질의 0.10이었다.
> 🧠 RRF는 한쪽 목록에만 든 청크를 크게 불리하게 만든다. 다음 할 일은 리랭커가 아니라 평가셋 보강과 융합 설정 실험이다. 리랭커는 2026-11-17에 보류하기로 했다.

## 전체 흐름 📄

```
[빌드할 때]  wiki/*.md → build-index.mjs(헤딩 기준 청킹) → chunks.json(3,808개, 커밋 고정) → embed.mjs → vectors.bin
[질문할 때]  질문 → BM25 상위 pool개 ┐
                  → 벡터 상위 pool개 ┴→ RRF로 순위 합치기 → top-k → (/api/ask) LLM 답변
```

- 코퍼스: 게임 85페이지(493청크) + AI 주간 소식 22페이지(3,315청크), 스냅샷 `22bc3cc`.
- 청크: 헤딩 경로(`상위 > 하위`)를 유지한 채 900자 이하로 자르고 60자 미만은 버린다. 각 청크 URL에 커밋 SHA를 넣어서 위키가 바뀌어도 평가를 같은 조건으로 다시 돌릴 수 있다.

| | BM25 (어휘) | 임베딩 (의미) |
|---|---|---|
| 보는 것 | 같은 글자·단어가 있나 | 뜻이 가까운가 |
| 강한 곳 | 고유명사, 모델명, 버전 | 동의어, 바꿔 말한 질문, 영어 질문 |
| 약한 곳 | 단어가 다르면 0점 | 드문 고유명사·숫자·부정("가능/불가") |

## BM25

### 역색인을 미리 만들 수 있는 이유 🧠
BM25 점수는 질문 토큰별 점수를 더한 값이다. 그래서 "토큰 → [(청크, 등장 횟수)]" 표(포스팅 리스트)를 미리 만들어 두고, 질문이 오면 그 토큰의 줄만 읽으면 된다. 질문 토큰이 하나도 없는 청크는 아예 보지 않는다. 벡터 검색은 질문 벡터가 와야 곱셈을 할 수 있어서 이렇게 미리 해 둘 수 없다.

📄 `loadIndex()`가 서버 기동 때 `inv`(역색인), `lens`(청크 길이), `avg`(평균 길이)를 만든다. 포스팅 길이가 곧 n(그 토큰이 든 청크 수)이다.

### 한글 bigram 토큰화 📄
한글은 두 글자씩 겹쳐 자른다("게이지가" → 게이·이지·지가). 조사가 붙어도 "게이지가"와 "게이지를"이 서로 걸린다. 영문·숫자는 단어 그대로 쓰고, `gpt-5.5`처럼 기호가 섞이면 `gpt`·`5`·`5`도 함께 넣는다. 색인 텍스트는 `제목 제목 헤딩 본문`이라 제목 단어가 두 배로 반영된다. 질문 토큰은 `new Set`으로 중복을 뺀다.

### 점수 공식 📄
```
score = Σ IDF(t) × tf×(k1+1) / (tf + k1×(1 − b + b×길이/평균))
IDF   = ln(1 + (N − n + 0.5)/(n + 0.5))      k1 = 1.2, b = 0.75
```
`1 +`가 붙은 Lucene 방식 IDF를 써서 흔한 단어도 IDF가 음수가 되지 않는다.

### 손으로 계산한 예 🧠
청크 4개(N=4, 평균 길이 4.5), 질문 "체력 붕괴".

| 청크 | 토큰 | 체력 | 붕괴 | 합계 |
|---|---|---|---|---|
| 2 | 자세 게이지 붕괴 체력 감소 회복 지연 (7) | 0.29 | 0.98 | **1.27** |
| 4 | 체력×3 회복 휴식 (5) | 0.55 | 0 | 0.55 |
| 1 | 체력 회복 포션 (3) | 0.41 | 0 | 0.41 |
| 3 | 상점 포션 가격 (3) | 계산 안 함 | | 0 |

- IDF: 체력(n=3) 0.36, 붕괴(n=1) 1.20. 드문 단어가 세 배 넘게 무겁다.
- 청크4는 "체력"이 3번이지만 청크1의 1.3배에 그친다(tf 포화).
- 같은 tf=1이라도 짧은 청크1(0.41)이 긴 청크2(0.29)보다 높다(길이 보정).
- k1은 포화 속도(0이면 있다/없다만 봄), b는 길이 보정 강도(0이면 길이 무시)다. 1.2와 0.75는 업계 관례값이다.

## 임베딩

### 내적이 유사도가 되는 이유 🧠
내적은 같은 위치끼리 곱해서 더한 값이고, 두 벡터가 얼마나 같은 방향을 가리키는지를 나타낸다. 📄 `embed()`가 모든 벡터를 길이 1로 정규화하므로 내적이 곧 코사인 유사도다.

이 값이 뜻을 반영하는 건 학습 때문이다. 임베딩 모델은 (질문, 맞는 문서) 쌍의 내적은 크게, 무작위 쌍은 작게 나오도록 대조 학습으로 훈련된다. 검색할 때 내적을 쓰는 건 모델이 학습한 기준을 그대로 쓰는 것이다. 그래서 질문과 문서는 반드시 같은 모델로 임베딩해야 한다.

한계:
- 비슷하다고 맞는 건 아니다. "환불 가능"과 "환불 불가"는 벡터가 가깝다.
- 점수의 절댓값(0.62 등)은 의미가 없고 순위만 믿을 수 있다.
- 모델이 학습 때 거의 못 본 말(직접 만든 게임 용어 등)에 약하다. 이 부분은 BM25가 보완한다.
- 여러 주제가 섞인 긴 청크는 벡터가 평균 방향으로 흐려진다.

### 전수 비교와 벡터 DB 🧠
📄 지금은 3,808개 전부와 곱한다(`dense()`). 1,024차원 기준 질문 1건에 곱셈 약 400만 번이라 몇 ms면 끝난다.

벡터 DB도 곱셈 결과를 미리 저장해 두지는 않는다. 미리 만들어 두는 건 비슷한 벡터끼리 모아 둔 배치다.
- **IVF**: k-means로 그룹을 나눈다. 질문이 오면 그룹 중심과 먼저 비교하고, 가까운 그룹 몇 개 안에서만 찾는다.
- **HNSW**: 가까운 벡터끼리 연결한 다층 그래프를 만든다. 질문과 더 가까운 이웃 쪽으로 이동하며 찾는다. pgvector·Qdrant 등이 지원한다.
- 대가: 근사 검색(ANN)이라 진짜 1등을 놓칠 수 있다. 인덱스 생성과 갱신에 비용이 든다.
- 언제 붙이나: 청크가 수십만 개를 넘거나 데이터가 실시간으로 추가·삭제될 때. 그때는 이미 쓰는 Supabase에 pgvector + HNSW를 거는 게 가장 손이 덜 간다.

## RRF (Reciprocal Rank Fusion)

### 점수 대신 순위를 쓰는 이유 🧠
BM25 점수는 상한이 없고 질문마다 단위가 다르다. 코사인은 0.3~0.8 근처에 몰린다. 그냥 더하면 BM25가 순서를 정해 버린다. min-max·z-score·가중합으로 맞추는 방법도 있지만 모두 점수 분포를 믿어야 하고, 가중합은 튜닝이 필요하다. RRF는 순서만 믿는다(Cormack 등, SIGIR 2009).

```
RRF(청크) = Σ 1/(60 + 순위)      목록에 없으면 그 목록에서는 0
```
📄 각 검색기에서 `pool = max(k×5, 30)`개를 뽑는다(k=8이면 40). 결과마다 `lexical`·`vector`에 원래 순위를 남긴다. 벡터가 꺼져 있으면 BM25 목록 하나로 RRF를 돌리는데, 이때 순서는 BM25와 같다.

### k=60의 의미 🧠
| 순위 | k=60 | k=1 |
|---|---|---|
| 1 | 0.0164 | 0.500 |
| 10 | 0.0143 | 0.091 |
| 40 | 0.0100 | 0.024 |

k=60에서는 1위와 10위 차이가 15%뿐이라, 몇 위인지보다 목록에 들었는지가 중요하다. 예: A(BM25 1위, 벡터 10위) vs B(3위, 2위). k=60이면 B가, k=1이면 A가 이긴다.

### 한쪽 목록에만 든 청크가 크게 불리하다 🧠
기본 설정(pool 40)에서는 양쪽 다 40위인 청크(0.0200)가 한쪽 1위 청크(0.0164)를 항상 이긴다. 이 성질은 pool ≤ 61일 때만 성립하고, rag-demo의 k=20(pool 100)에서는 아니다.

문제가 되는 경우:
- **영어 질문**: 정답은 벡터 1위인데 BM25 쪽에는 없다. "system"만 맞은 무관한 청크가 BM25 35위·벡터 38위로 정답을 이긴다.
- **고유명사 질문**: 정답은 BM25 1위인데 벡터 45위라 pool 밖으로 잘려서 진다.
- 📄 동점이면 먼저 넣은 BM25 결과가 앞선다(안정 정렬). 영어 질문에서 무관한 BM25 1위가 정답인 벡터 1위보다 먼저 나올 수 있다.

원인은 두 가지다. pool 밖이면 0점이 되는 절벽, 그리고 k=60이 순위 차이를 작게 만드는 것이다.

### 검토한 대안과 판단 🧠
- **k 낮추기**: 효과가 있다(k=20이면 공통 청크가 양쪽 21위 안이어야 한쪽 1위를 이긴다). 대신 "단어만 맞고 뜻은 틀린 BM25 1위"도 함께 세진다. 그래서 채택하지 않는다.
- **벡터 순위를 끝까지 쓰기**: `dense()`는 이미 전부 계산하므로 비용이 없다. BM25 오답 1위를 키우지 않는다. 채택 후보다.
- **벡터 가중치**: 영어 질문에서는 1.5 정도면 정답이 이긴다. 하지만 고유명사 질문에서 "비슷한 다른 대상"이 올라올 수 있어 한국어 hit@1 1.00이 깨질 위험이 있다. 1.0/1.2/1.5를 평가로 정한다.
- **평가셋 공백**: 지금 평가셋에는 "단어는 맞는데 뜻이 다른" 질문이 없어서 가중치를 근거 있게 정할 수 없다. 이런 질문을 10개쯤 추가해야 한다.
- **질문별 가중치**: BM25 1위가 질문 단어를 얼마나 덮었는지 보고 낮으면 BM25 비중을 줄인다. 위 방법으로 부족할 때 쓴다.

## 리랭커 (보류)

### 개념 🧠
리랭커는 1차 검색이 고른 후보 30개 정도를 질문과 짝지어 다시 읽고, 관련도를 직접 매겨 순서를 다시 정하는 모델이다(cross-encoder).

| | 임베딩 (bi-encoder) | 리랭커 (cross-encoder) |
|---|---|---|
| 입력 | 질문·청크 따로 | `[질문]+[청크]` 함께 |
| 미리 계산 | 가능 | 불가(질문마다 짝을 새로 만듦) |
| 정확도 / 속도 | 보통 / 빠름 | 높음 / 짝마다 모델 1회 |

임베딩은 어떤 질문이 올지 모르는 채로 청크를 벡터 하나로 압축한다. 그래서 부정, 대상, 조건 같은 세부가 뭉개진다. 리랭커는 질문의 각 단어가 청크의 각 단어를 직접 참조(attention)해서 문맥으로 판단한다. 비유하면 임베딩은 서류 심사, 리랭커는 면접이다.

### 붙이면 달라지는 것 🧠
- RRF의 역할이 "정답을 1등으로"(hit@1)에서 "정답을 30등 안에"(hit@30)로 바뀐다. 위의 가중치·k 고민이 대부분 사라진다.
- 리랭커 점수는 질문이 달라도 비교적 일정한 척도로 나온다. 그래서 "최고 점수가 기준 미만이면 근거 없음"으로 `/api/ask`가 모른다고 답하게 할 수 있다.
- 선택지: 리랭크 API(Cohere·Jina·Voyage, 대부분 유료), 오픈 모델(bge-reranker-v2-m3, 다국어, 서버 필요, Vercel 함수에는 부적합), 지금 쓰는 `WIKI_LLM` 채팅 모델로 0~10점 채점(추가 서비스 없음, 느리고 쿼터 소모).
- 한계: 후보에 없는 정답은 못 살린다. 30쌍이면 CPU 기준 1~3초가 더 걸린다. 입력이 약 512토큰이라 900자 청크 끝이 잘릴 수 있다. 한국어 성능이 모델마다 다르다.

### 결정 (2026-11-17, 사용자 확인) 📄
리랭커는 지금 적용하지 않는다. 무료 쿼터와 규모를 고려해 다음 순서로 진행한다.
1. 평가셋에 "단어 함정" 질문 추가
2. 벡터 순위를 끝까지 사용
3. 벡터 가중치 1.0/1.2/1.5 비교

그래도 영어·동의어 구간이 오르지 않으면 LLM 리랭크부터 실험한다.
