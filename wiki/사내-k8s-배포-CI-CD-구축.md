> [!tip] 핵심 takeaway
> 🧠 **SM 시절의 인프라 감각을 "컨테이너·쿠버네티스·CI/CD"로 업데이트한 첫 실전.** 서버 지식이 거의 없는 상태에서 **이틀 만에** 공용 운영 클러스터 구조를 읽고 → 남의 서비스에 영향 없이 내 서비스를 올리고 → "브랜치 병합 = 1~2분 뒤 자동 반영" 파이프라인까지 만들었다.
> 🧠 포트폴리오 포인트는 기술 나열보다 **제약 속 설계 판단**: ① 공용 서버라 "조회 먼저, 내 칸만, 영향 실측" ② CI 서버가 사내망에 못 들어온다는 걸 **시험으로 먼저 확인**하고 배포 방향을 뒤집음(push → pull) ③ ARM 빌드 서버에서 에뮬레이션 없이 x86 이미지 만들기.
> 📄 결과: 병합 → **약 1분 15초 뒤 운영 반영**, 서버 수동 작업 0회(2026-11-04 실측).

## 문제

- 📄 팀원들이 쓰는 연동 테스트 도구가 **내 PC 에서만** 돌았다. 공유하려면 각자 설치해야 했다.
- 📄 회사에 공용 쿠버네티스 클러스터가 있었지만, 다른 팀의 운영 서비스가 돌고 있는 **공유 자원**이었다. 문서(구성도 PPT)는 있었지만 실제와 일치하는지 몰랐다.
- 📄 나는 서버 지식이 부족했다 — "이 부분을 공부하고 더 잘 알고 싶다"가 동기의 절반.

## 접근 — 3단계

### 1) 조회만 하며 구조 파악
- 📄 원칙: **"같이 쓰는 서버니까 변경하지 말고 조회만."**
- 📄 노드·Pod·Service·Ingress·리소스 사용률을 조회하고 PPT 구성도와 대조 → 문서에 없는 구성요소(검색엔진 클러스터)를 찾았다.
- 📄 요청이 들어오는 길(가상 IP → Ingress 컨트롤러 → 경로 규칙 → Service → Pod)을 실제 설정으로 따라가 그렸다.
- 🧠 이 단계에서 가용성·백업·정리 대상 같은 운영 관찰점도 나왔지만, **목표(내 서비스 올리기)와 분리**해 별도로 기록만 했다. 범위를 지킨 판단.

### 2) 내 칸(네임스페이스)에만, 영향은 실측으로
- 📄 내 전용 네임스페이스를 만들고 그 안에만 리소스를 두었다 → **삭제는 명령 한 줄**로 흔적 없이 가능.
- 📄 핵심 발견: 기존 서비스의 Ingress 가 **호스트를 지정하지 않은 "나머지 전부" 규칙**이었다. 같은 도메인을 쓰면 기존 서비스 요청을 가로채게 된다 → **별도 도메인**으로 분리.
- 📄 배포 후 **같은 IP 에 Host 헤더만 바꿔 요청**해, 새 서비스는 200 · 기존 서비스는 배포 전과 같은 응답(302)인 것을 숫자로 확인.
- 📄 비밀값: 토큰은 최소 권한(읽기 전용) · 키는 저장소·문서·쉘 히스토리 어디에도 남기지 않음(표준입력 붙여넣기 방식).

### 3) CI/CD — 시험으로 제약을 먼저 확인
- 📄 처음 설계는 "CI 가 빌드하고 kubectl 로 배포". 구현 전에 **정보만 출력하는 시험 파이프라인**을 돌렸다.
- 📄 결과: CI Runner 는 **클라우드(AWS)의 ARM 서버**였고, **사내 클러스터에 접근 불가**, 레지스트리는 접근 가능.
- 🧠 → 설계를 뒤집었다. **CI 는 이미지를 레지스트리에 올리기만(push), 클러스터 안의 작은 CronJob 이 2분마다 새 이미지를 확인해 가져간다(pull).**

```
deploy 브랜치 병합 → CI(클라우드, ARM): 빌드 → 레지스트리 push (:deploy, :커밋해시)
                                                        ↑ 2분마다 지문(digest) 비교
                              사내 클러스터: CronJob → 바뀌었으면 rollout restart → 롤링 업데이트
```

## 핵심 설계 판단 (트레이드오프)

| 결정 | 대안 | 고른 이유 |
|---|---|---|
| **pull 방식 CD** (클러스터 안 CronJob) | CI 에서 kubectl / GitLab Kubernetes Agent / ArgoCD·Keel | 📄 Runner 가 사내망 불가, Agent 는 GitLab 관리자 설정 필요. 🧠 GitOps 도구는 클러스터 전역 설치라 공용 서버에 흔적이 큼. CronJob 은 **내 네임스페이스 안에서 완결** |
| **권한을 네임스페이스·리소스 하나로 한정** (Role) | 관리자 kubeconfig 사용 | 🧠 자동화 계정이 털려도 다른 서비스는 못 건드림. 공용 서버에서 가장 중요한 축 |
| **두 단계 Dockerfile** — 설치는 빌드 머신 아키텍처, 최종 이미지엔 복사만 | QEMU 에뮬레이션 설치 | 📄 Runner 에 x86 에뮬레이션 없음. 🧠 공용 CI 서버 커널 설정을 바꾸지 않아도 됨. 전제: 의존성이 순수 JS(네이티브 모듈 추가 시 재검토 — Dockerfile 에 주석) |
| **2분 간격** | 5분 | 🧠 하루 720회·회당 수 초·0.05코어 상한 → 기존 헬스체크(하루 약 1.3만 회)의 5% 수준. 사용자 확정 |
| **CI 로그인은 작업 종료 시 만료되는 토큰** | 개인 토큰 등록 | 🧠 공용 shell Runner 에 내 자격증명이 남지 않음 |
| **배포 브랜치 분리** — `deploy` 병합 = 운영 배포 | main 푸시 즉시 배포 | 📄 사용자 아이디어. 평소 작업은 자유롭게, 서버 반영은 의식적인 한 번의 병합으로 |

## 트러블슈팅

1. **이미지 push 거부 (`insufficient_scope`)** — 레지스트리 경로를 짐작으로 썼다. 📄 레지스트리 경로 = Git 프로젝트 전체 경로라는 규칙을 확인하고 수정.
2. **CI 설정 파싱 오류** — 셸 명령 안의 `"Host: x"` 의 `: ` 를 YAML 이 키:값으로 읽음. 📄 `- |` 블록 문자열로 해결.
3. **자동 교체가 영원히 안 일어날 뻔** — CronJob 이 매번 "배포 진행 중"이라며 건너뜀. 📄 원인: `kubectl rollout status` 는 **watch 권한**이 필요한데 최소 권한 Role 에 없어 실패 → 스크립트가 실패를 "진행 중"으로 해석. `kubectl auth can-i ... --as=<서비스계정>` 로 검증. 📄 해결: 권한을 늘리지 않고 **get 으로 상태 숫자만 읽어 판정**, kubectl 실패는 job 실패로 드러나게 → 권한은 오히려 축소.
   - 🧠 교훈: **"실패를 정상 분기로 삼키는 스크립트"가 가장 위험하다.** 최소 권한 원칙과 실패 노출은 한 세트.
4. **공용 CI 서버에 남이 만든 빌더가 기본으로 설정됨** — 📄 건드리지 않고 내 작업에서만 `--builder default` 를 명시.

- 📄 사내 전용 도메인으로 서비스 운영 — 팀원은 hosts 한 줄 추가 후 브라우저로 바로 사용(설치 불필요).
- 📄 **병합 → 약 1분 15초 뒤 운영 반영**, 서버 수동 작업 0회 (2026-11-04 실측: 문서 목록 변경이 자동 반영됨).
- 📄 기존 서비스 응답 변화 없음(배포 전후 실측 비교).
- 📄 문서 탭: 저장소의 `.md` 를 요청마다 읽어 렌더 → **문서 한 벌**로 GitHub·GitLab·서비스 화면이 같이 바뀜. 화이트리스트로 경로 조작(`../.env`) 차단, 문서 내 앵커 158개 전수 검증.
- 📄 운영 문서 2종: 클러스터 관리자용(추가 리소스·네트워크·영향·삭제 방법) + 팀 공유 글.
- 📄 자체 점검 `npm test` 66항목(문서 라우트·404·앵커 점검 추가).

## 배운 것 — 인사이트 🧠

1. **"조회 → 격리 → 실측" 순서가 공용 인프라의 예의이자 안전장치다.** 변경 전에 구조를 읽고, 내 칸에만 만들고, 영향은 말이 아니라 같은 요청의 응답 비교로 증명한다. SM 시절 운영 서버를 다루던 감각이 그대로 통했다.
2. **설계 전에 환경을 시험하라.** 아무것도 바꾸지 않는 진단 파이프라인 두 번이 "CI 에서 kubectl"이라는 처음 설계가 불가능함을 구현 전에 알려줬다. 만들고 나서 알았으면 하루를 버렸을 것.
3. **방향을 뒤집으면 제약이 사라진다.** 들어갈 수 없으면 가져오게 한다(push → pull). 이미 열려 있는 길(클러스터 → 레지스트리)을 재사용하는 게 새 길을 뚫는 것(방화벽·에이전트)보다 싸다.
4. **최소 권한은 공짜가 아니다.** 권한을 줄이면 명령이 조용히 실패할 수 있다. 권한 설계와 "실패를 숨기지 않는 스크립트"를 함께 설계해야 한다.
5. **이동 태그(`:deploy`)의 대가는 롤백 방식이다.** 단일 태그 + 항상 pull 은 단순하지만 `rollout undo` 가 의미 없어진다 → 되돌리기는 Git(브랜치 revert)으로. 운영 문서에 명시.
6. **아키텍처 차이(ARM vs x86)는 이제 기본 고려사항.** 맥(M 시리즈)·클라우드 ARM 서버·x86 운영 노드가 섞이는 게 보통이다. "실행이 필요한 단계"와 "복사만 하는 단계"를 나누면 에뮬레이션 없이 해결된다.
7. **AI 와 함께 배우는 방식** — 명령은 내가 직접 치고, AI 는 "왜 이 명령인지·결과 각 줄의 의미"를 설명하게 했다. 결과를 붙여넣고 해석을 받는 루프가 서버 학습 속도를 크게 올렸다. 위험한 자동화(관리자 원격 접속)는 도구가 막았고, 그 경계를 우회하지 않고 사람이 실행하는 구조로 바꿨다 — [[에이전트-자동화-도구]]의 "사람이 승인하는 지점" 설계와 같은 결.
