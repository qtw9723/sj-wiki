> [!tip] 핵심 takeaway
> 🧠 이 모델의 핵심은 **곡(sheet)과 세트(set)를 분리**하는 것. 메모는 세트가 아니라 **곡에 붙는다** — 그래야 같은 곡이 다음 주에 다시 나와도 필기가 따라온다(📄 D1).
> 📄 원본은 형식이 제각각(PDF·이미지)이지만 **업로드 시점에 PDF로 정규화**해 저장한다(D6). 이후 병합·뷰어·페이지 관리가 전부 단순해진다.

---

## 1. 저장소 구조 (📄 D6 + 🧠 이중 보관)

📄 "악보 저장은 NAS 혹은 클라우드에 해두고, 웹이나 앱에서 불러서 사용하는 방식"

```
원본 (original)      ← 사용자가 올린 그대로. PDF / JPG / PNG. 절대 수정하지 않음
   ↓ 업로드 시 변환
정규화본 (normalized) ← 전부 PDF. 뷰어·병합·페이지 인덱싱은 전부 이걸 사용
   ↓ 파생
썸네일 (thumb)        ← 목록 화면용 첫 페이지 이미지
```

- 🧠 **이중 보관을 권장**하는 이유: 변환 로직이 나중에 개선되면 원본에서 다시 뽑을 수 있다. 원본을 버리면 되돌릴 수 없다.
- 🧠 파일 접근은 **서명 URL(만료 있는 임시 링크)** 로. 스토리지를 공개 버킷으로 열지 않는다.

### 1-1. 저장소 결정 (📄 2026-08-27 사용자 확정)

| 단계 | 저장소 | 비고 |
|---|---|---|
| **프로토타입** | 📄 **본인 Supabase (임시)** | 📄 NAS 불가, 별도 클라우드도 당장 어려움 → 비계(scaffold)로 사용 |
| **운영** | 📄 **미정 — 클라우드로 간다면 AWS 유력** | 교회 이관 시점에 재결정 |

> [!warning] 🧠 Supabase는 "버릴 것"으로 전제하고 쓴다
> 📄 사용자 확정: "이건 실제로 운영할 때 쓸 게 아니라 임시로 쓰는 것." → 설계 목표는 **Supabase를 잘 쓰는 것이 아니라 나중에 떼어낼 때 아프지 않게 쓰는 것**이다.

- 🧠 **기존 [[parking]] 공유 인스턴스에 얹지 않는다.** 새 Supabase 프로젝트를 별도로 판다.
  - 근거: [[parking]] 문서 자체가 "단일 장애점 — 잘못 건드리면 동시에 깨진다"고 경고. 현재 [[notepad]]·[[mailer]]·[[schedule-reporter-kakao]]·[[CogInsight-Generator]]가 전부 의존하고, parking은 사내 교육용 실서비스로 전환된 상태.
  - 분리하면 ① 용량 한도를 따로 받고 ② 백은률에게 이 프로젝트 권한만 줄 수 있고 ③ 교회 이관 시 통째로 넘기거나 버리기 쉽다.
- 📄 Supabase Free 플랜 한도 (2026-08-27 확인): DB 500 MB · 스토리지 1 GB · 파일 업로드 최대 50 MB · 월 대역폭 5 GB · MAU 50,000.
  - 🧠 환산: 악보 약 700~2,000장, 20명이 주 1세트 열람 시 월 대역폭 1 GB 미만 → **프로토타입은 물론 초기 실사용까지 무료로 충분**.
  - ⚠️ 📄 **무료 플랜은 1주일 미사용 시 프로젝트가 일시정지**된다. 실사용 중에는 매주 쓰이니 무관하지만, **개발이 뜸한 기간 뒤 시연일에 정지돼 있을 수 있다** → 시연 전 상태 확인 필수.

### 1-2. AWS 이전 매핑 (🧠 — 운영 전환 시)

| Supabase | AWS 대응 | 이전 난이도 |
|---|---|---|
| Postgres | RDS / Aurora | 쉬움 — 그냥 Postgres. 덤프·복원 |
| Storage | S3 | 쉬움 — S3 호환이라 경로 규칙 유지 |
| RLS 정책 | (그대로) | Postgres 기능이라 따라옴 |
| **Auth** | Cognito / 자체 로그인 | ⚠️ **진짜 락인 지점** → [[악보-아카이브-인증-권한]] §3-3 |
| Edge Functions | Lambda | Deno → Node 포팅 필요 |
| Realtime | 대응물 애매 | ⚠️ **아예 쓰지 않는다** (아래) |

**락인 회피 규칙 (🧠 — 딱 이 3가지만 지킨다)**

1. **DB에는 `storage_path`만 저장한다.** 전체 URL 금지. (예: `sheets/{sheet_id}/normalized.pdf`)
2. **파일 읽기·쓰기·서명URL 발급을 한 모듈에 모은다** (`storage.ts` 하나). Supabase 클라이언트 호출을 UI 컴포넌트에 흩뿌리지 않는다.
3. **Realtime을 쓰지 않는다.** 현 설계에 실시간이 필요한 지점이 없고(메모는 append-only 동기화로 충분 → [[악보-아카이브-메모-동기화]]), 한 번 쓰면 AWS 대응물 찾기가 성가시다.

> [!tip] 🧠 과하게 추상화하지 말 것
> 프로토타입에 인터페이스 레이어를 겹겹이 쌓으면 정작 검증할 것(카톡 대신 여는가 · 펜슬 필기가 쓸만한가)이 늦어진다. 위 3가지만 지키면 **갈아끼울 때 손댈 파일이 한 자리수**로 유지된다. 그 이상은 지금 하지 않는다.

## 2. 핵심 테이블 (🧠 초안)

> [!warning] `team_id` 규약
> 아래 `team_id`가 붙은 모든 테이블은 [[악보-아카이브-인증-권한]] §4 규약을 따른다. **첫 마이그레이션부터 포함**한다.

### `teams` / `users` / `memberships`
→ [[악보-아카이브-인증-권한]] §4 참조. `users`는 `team_id`를 갖지 않고 `memberships`로 연결.

### `sheets` — 악보(곡) 1건
| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `team_id` | 소속 팀 |
| `title` | 📄 곡 제목 (검색 대상) |
| `composer` | 작곡가 |
| `key` | 조(key) |
| `tempo`, `time_signature` | 🧠 선택 |
| `tags` | 🧠 분류용 (경배/찬양/특송 등) — 📄 요구 6 "검색의 다양성" |
| `lyrics_text` | 📄 D5. 가사 전문. **전문 검색(full-text search) 인덱스 대상** |
| `original_file_path` | 원본 파일 |
| `normalized_pdf_path` | 정규화 PDF |
| `page_count` | 페이지 수 (메모 좌표 검증용) |
| `created_by`, `created_at`, `updated_at` | |

### `sets` — 예배 곡목 (📄 요구 2)
| 컬럼 | 설명 |
|---|---|
| `id`, `team_id` | |
| `title` | 예: "2026-08-30 주일 3부" |
| `service_date` | 📄 예배 날짜 — 지난 곡목 검색의 핵심 축 |
| `share_token` | 📄 D8. 링크 배포용 추측 불가 토큰 (UUID) |
| `note` | 📄 요구 2 "곡목에 대한 메모" (세트 단위 메모) |
| `created_by`, `created_at` | |

### `set_items` — 세트 안의 곡 순서
| 컬럼 | 설명 |
|---|---|
| `set_id`, `sheet_id` | |
| `position` | 순서 |
| `key_override` | 🧠 이번 주만 다른 키로 할 때 |
| `song_form_override` | 📄 D4 + 🧠. 인도자가 이번 주만 2절 생략 같은 변형을 줄 때 |
| `item_note` | 🧠 이 세트에서 이 곡에 대한 메모 (예: "간주 4마디로 줄임") |

### `annotations` — 메모 (📄 D1·D2)
→ 상세는 [[악보-아카이브-메모-동기화]]. 요점만:
- **`sheet_id`에 붙는다** (`set_id` 아님). 📄 D1
- `layer`: `personal` / `shared` — 📄 D2
- `page`, 좌표 데이터, `user_id`, `team_id`

## 3. 송폼(song form) 처리 — 📄 D4

📄 사용자 결정: **"송폼은 자동추출 말고, 공용메모로 활용하면 될 것 같아"**

- 🧠 근거: OMR로 음표는 읽어도 `Intro–V1–V2–C–B–C–Outro` 같은 **구성은 기계가 만들 수 없다**. 사람 입력이 맞다.
- 🧠 구현 형태: 공용 메모 레이어(`layer='shared'`)의 한 종류로 저장하되, **`kind='song_form'` 같은 구분 필드**를 둬서 나중에 구조화할 여지를 남긴다.
  - MVP: 그냥 텍스트 메모 (`"Intro-V1-C-V2-C-B-C-Outro"`)
  - 이후: 뷰어 상단에 송폼 바를 띄우고 탭하면 해당 마디로 점프 (🧠 실전 가치 큼)
- 📄 세트별 변형은 `set_items.song_form_override`로 받는다.

## 4. 스캔·메타데이터 자동화 — 📄 D5

📄 사용자 결정: **"스캔은 1단계와 가사 정도만 스캔해서 검색에 활용해도 문제 없어. 나머지 정보는 메모로 처리해도 될 것 같아."**

| 단계 | 내용 | 난이도 | 채택 |
|---|---|---|---|
| **1단계** | 악보 첫 페이지 상단 OCR → 제목·작곡가·키 추출 | 쉬움 | ✅ 채택 (Phase 3) |
| **1.5단계** | 가사 영역 OCR → `lyrics_text` 저장 → 전문 검색 | 중간 | ✅ 채택 (Phase 3) |
| 2단계 | 코드 심볼 인식 → 검색 인덱스 | 중간 | ❌ 보류 |
| 3단계 | 전체 OMR → MusicXML → 자동 조옮김 | 어려움 | ⏸ 먼 로드맵 |

- 🧠 1단계만으로도 **악보 등록 노동의 대부분이 사라진다** — 이게 자동화의 실익이 가장 큰 지점.
- 🧠 OCR 결과는 **자동 확정하지 않고 "제안값"으로** 채워 넣고 사람이 확인하게 한다. 오인식된 제목이 검색을 오염시키는 게 더 나쁘다.
- 📄 나머지 정보(편곡 메모, 주의사항 등)는 전부 메모로 처리.

## 5. 검색 (📄 요구 6 "악보 검색의 다양성")

🧠 검색 축 제안:
- 제목 / 작곡가 (기본)
- **가사 일부** (📄 D5 — "그 가사 있는 곡 뭐였지?"가 실제로 가장 흔한 탐색 방식)
- 키 · 태그(경배/찬양/특송)
- **지난 곡목 기준**: "이 곡 마지막으로 언제 했지?" / "최근 3개월간 안 한 곡" — 🧠 이건 카톡이 절대 못 하는 것이고, **이 서비스를 쓸 이유 그 자체**다. 우선순위 높게 볼 것.
