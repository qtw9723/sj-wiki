> [!tip] 핵심 takeaway
> 🧠 [[올림푸스-Olympus]]에 넣는 기획서는 **"사람에게 설명하는 일반 계획서"가 아니라 "기획자(메티스)가 분석·분해·개발·검증·배포까지 자동으로 굴리도록 지시하는 요청서"**다. 그래서 ① **수용 기준은 테스트로 판정 가능**하게 ② **가정 불가한 결정은 "진짜 블로커"로 명시** ③ **검증·배포 방법을 함께** 적는 게 핵심.
> 🧠 잘 쓴 요청서 = 사람 개입 최소화. 애매하면 메티스가 "합리적 가정"으로 그냥 진행해버리므로, **꼭 사람이 정해야 하는 것만 블로커로** 콕 집어야 폰으로 물어본다.

## 이 문서의 용도
📄 `spec/<프로젝트>/*.md`에 넣을 기획요청서를 이 요령대로 작성한다. 넣고 `bash run.sh` 하면 [[올림푸스-Olympus]]가 분석→(블로커 폰승인)→구현→verify→(최종 폰승인)→자동머지→배포→아카이브까지 굴린다.

---

## 1. 메티스가 요청서를 어떻게 읽는가 (왜 이렇게 써야 하나)
🧠 이해하고 쓰면 실수가 준다.

- **요구사항 분석**: 요청서를 읽고 `requirements.md`로 분석 → 작은 작업들(`backlog.md`)로 분해한다. → **목적·요구·범위가 명확할수록 분해가 정확**.
- **모호함 처리**: 애매한 건 **멈추지 않고 "합리적 가정"으로 진행**하고 `open-questions.md`에 쌓아 끝에 한 번에 보고한다. → **가정되면 곤란한 건 반드시 "블로커"로 못 박아야** 폰으로 물어본다.
- **그라운드 트루스**: LLM 합의가 아니라 **실행되는 게이트(`VERIFY_CMD`: lint·test·build)**가 심판. → **수용 기준을 테스트로 판정 가능**하게 써야 한다.
- **기존 코드 보존(brownfield)**: 기존 repo면 최소 변경·동작 보존 원칙. **기존 테스트 green 유지**가 기본 수용 기준.

## 2. 필수 구성요소 (체크리스트)
> [!info] 이 7개가 있으면 사람 개입 없이 잘 굴러간다
> - [ ] **목적/배경** — 무엇을·왜 (한두 문단)
> - [ ] **대상 repo** — 어느 프로젝트를 고칠지 (폴더명 = repo명, 아래 §4 주의)
> - [ ] **요구사항 명세** — 구체적 동작 + **입력→출력 예시**
> - [ ] **수용 기준(AC)** — **테스트로 판정 가능**하게. 기존 테스트 green 유지 포함
> - [ ] **⚠️ 진짜 블로커** — 가정 불가·반드시 사람이 정해야 하는 값 (없으면 "없음"이라고)
> - [ ] **범위 밖(YAGNI)** — 하지 말 것
> - [ ] **검증·배포** — `VERIFY_CMD`와 배포 규약(명령)

## 3. 복붙 템플릿
```markdown
# <프로젝트/기능 제목>

## 목적
<무엇을, 왜. 한두 문단. 사용자·시나리오.>

## 대상
- repo: <예: notepad → ~/IdeaProjects/notepad>
- 수정 파일(예상): <예: src/lib/tags.js, 그 테스트>
- 이 범위 밖 파일은 건드리지 않는다.

## 요구사항 (동작 명세)
1. <구체적 규칙 1> — 예: `'#work'` → `'work'`
2. <구체적 규칙 2> — 예: `'Side Project'` → `'side-project'`
3. 처리 순서/엣지케이스: <...>

## ⚠️ 반드시 사람에게 확정받아야 하는 값 (가정 금지 — 진짜 블로커)
- <이게 없으면 개발 시작 불가하고, 임의 가정하면 안 되는 것.
  예: 기존 저장 데이터와 호환돼야 하는 포맷·구분자, 외부 연동 자격증명, 핵심 데이터모델 선택>
- (해당 없으면: "없음 — 모두 합리적 가정으로 진행 가능")

## 수용 기준 (그라운드 트루스)
- `<VERIFY_CMD>` 전부 통과 (예: npm run verify = lint + test + build)
- <신규 동작>을 검증하는 테스트가 추가되어 통과
- 기존 테스트 전부 green 유지(회귀 없음)

## 범위 밖 (하지 말 것)
- <YAGNI 항목들>

## 배포
- <배포 명령 한 줄. 예: git push origin main → Vercel 자동배포>
- (배포 안 하거나 규약 없으면 생략 → 올림푸스가 완료 시 물어본다)
```

## 4. 작성 팁 & 함정
🧠 이번에 실제로 굴려보며 얻은 것들.

- **대상 repo는 되도록 명시**: spec 폴더가 여러 개면 올림푸스가 **알파벳순 첫 폴더**를 고른다(예: `Mindboard`가 `notepad`보다 앞섬). 실행 시 `TARGET_REPO=...`로 지정하거나 spec 폴더를 하나만 두는 게 안전. 📄
- **버전별 spec 폴더 (2026-07-09 규약)**: 지속 개발 프로젝트는 폴더명에 버전을 붙인다 — `spec/<repo명>-vX.Y.Z/`(예: `CogInsight-Generator-v0.4.0`). state가 `state/<PROJECT>/`로 격리되므로 **한 버전 작업 중에 다음 버전 기획을 병행 준비** 가능. 📄
- **spec/<프로젝트>/run.env 필수 동봉 (2026-07-09 개선, 커밋 `d3bc670`)**: 폴더명 ≠ repo명일 때 큐/UI 실행이 빈 디렉토리를 greenfield로 만들어버린 실사고 후 도입. **기획서와 함께 `run.env`를 만들어** `TARGET_REPO`·`GIT_BRANCH`·`VERIFY_CMD`·`AUTO_MERGE` 등을 선언하면 run.sh가 자동 로드 — **UI/큐에서 실행해도 수동 env 없이 항상 올바른 대상**을 잡는다(우선순위: 명시적 env > run.env > config 기본값). 📄
- **"진짜 블로커"는 메티스 기준에 맞춰 표현**: 메티스는 *"개발을 시작조차 못 하고, 가정으로 대체 불가한 것(핵심 데이터모델·외부 자격증명)"* 일 때만 멈춘다. 단순 취향 선택은 가정으로 진행해버림 → 블로커로 만들려면 **"기존 데이터와 호환돼야 함 / 틀리면 깨짐 / 나는 알 수 없음"** 같은 **불가역·비가정성**을 근거로 적어라. 📄
- **AC는 반드시 실행 검증 가능하게**: "잘 되게" 말고 `입력 X → 출력 Y`처럼. 그래야 verify가 심판이 된다.
- **배포 규약은 명령 그대로**: 메티스가 그 명령줄을 `state/deploy.md`로 뽑아 머지 후 실행한다. 안 적으면 완료 시 폰/터미널로 "배포 명령 입력 또는 skip"을 묻는다. 📄
- **범위를 좁게**: 한 요청서 = 작은 목표 하나. 크면 여러 spec으로 나눠라(각각 분석·개발·아카이브 사이클).

### 🆕 (2026-08-07) 업계 근거로 뒷받침된 항목들 — [[AI-주간-소식-2026-W32]] 10·11차 보강

- ⭐ 🧠 **"애매한 요청서"를 처음으로 측정할 방법이 생겼다** (연결점 ㊵): 📄 arXiv **Toward Uncertainty Quantification in Modern Art**([2608.04038](https://arxiv.org/abs/2608.04038)) — *같은 작품을 다른 시드로 애니메이션하면 눈에 띄게 다른 영상이 나온다(시드마다 하나의 해석). **현대 미술은 의도적으로 애매하므로 이 불일치는 노이즈가 아니라 신호다.***
  - 🧠 논리를 이 문서로 옮기면: **같은 요청서를 N회 돌려 산출이 크게 갈리면, 그건 파이프라인 불안정이 아니라 요청서가 애매하다는 신호**다. 🧠 지금 이 문서의 팁들(*AC는 실행 검증 가능하게* · *블로커는 불가역·비가정성으로*)은 전부 **정성적 조언**이었는데, 산출 분산은 **숫자**다.
  - ✅ 🧠 실행 후보(순수 제안, 미구현): 요청서 확정 전에 **분석 단계만 N회 반복 실행**해 산출(작업 분해·AC 해석)의 분산을 보고, 분산이 크면 요청서를 다시 쓴다. 이건 위 *"진짜 블로커"* 판정을 사람 감에서 관측으로 옮기는 방법이다.
- 🧠 **"불충분하게 명세된 요청"이 논문 주제라는 근거가 셋으로 늘었다** (연결점 ⑰·㊵): 📄 **Asking Questions the Right Way**(*출력 품질이 사용자 프롬프트에 제약되고, **반복적 멀티턴 프롬프팅은 문맥 열화·인지적 수익 체감**을 낳는다*) · 📄 **CRAFTS**(*엔지니어가 **불충분하게 명세된 요청**을 결합된 결정으로 번역해야 한다*) · 위 미술 논문(애매함의 정량화). 🧠 이 문서를 *내 개인 노하우 메모*가 아니라 **업계가 연구 중인 문제의 실무 해법**으로 서술할 수 있다 → [[프로젝트-포트폴리오]].
- ⚠ 🧠 **한국어 요청서에 특정 리스크가 있다** (연결점 ㉛): 📄 arXiv **An Actionable Diagnosis of Multilingual, Multi-Agent Planning Failures**([2608.03735](https://arxiv.org/abs/2608.03735)) — *다국어 멀티에이전트는 **영어를 벗어나면 상당히 저하**되지만, 선행 연구는 **사용자 요청이 실행 가능한 계획으로 변환될 때 과제에 결정적인 정보가 어떻게 손실되는지**를 좀처럼 특정하지 않는다.*
  - 🧠 이 문서가 다루는 구간이 정확히 *"요청 → 실행 가능한 계획"* 이고, 요청서는 **한국어로 쓴다**. 🧠 실행 함의는 이미 있는 팁의 강화다 — *AC를 `입력 X → 출력 Y`로 쓰라*는 규칙은 **손실되면 즉시 드러나는 형태로 쓰라**는 뜻이 되고, 자연어 서술이 길수록 손실 위험이 커진다.
  - ⚠ 🧠 📄 언어별 손실 규모는 원문 절단으로 확인 불가 → *"한국어면 나쁘다"* 로 쓰지 않는다. 말할 수 있는 건 **"위키가 아직 측정해본 적 없는 축"** 까지다.
- 🧠 **"에이전트"라는 단어를 먼저 확인하라**(연결점 ③, 기존 항목 재확인): 한 수집분에서 *LLM 자율 에이전트 / 노코드 워크플로 노드 / 서버 상주 데몬* 3가지 뜻으로 쓰였다. 요청서에 "에이전트"가 등장하면 **어느 쪽인지 한 줄로 못 박는다.**
- 🚨 ⭐ 🆕 **(2026-08-08) 이 문서가 다루는 루프가 「공무원 입문서」와 「시리즈A 스타트업」에 동시에 나타났다** (연결점 (51)·㊾ — [[AI-주간-소식-2026-W32]] 13·14차 보강):
  - 📄 신간 **「공무원 AI 54제」**(AI 자동화 실전 가이드) 구성 = *반복 업무 중 **자동화할 일 선정** → **업무지시서 작성** → **결과 검토** → **지침 개선***. 🧠 이 4단계는 이 문서의 「요청서 작성 → 실행 → verify → 팁 갱신」 루프와 **같은 것**이다.
  - 📄 같은 날 **나이브(Naïve)** 가 *Cursor·Claude Code·Codex에 연결하는 프롬프트 레이어*로 시리즈A **2,850만 달러**를 유치했다.
  - 🧠 함의: 이 루프는 **위로는 독립 투자 대상, 아래로는 공무원 기초 소양**이 됐다 — *"루프를 안다"* 는 더 이상 차별점이 아니다. 🧠 남는 차별점은 **이 문서의 팁 목록 자체**다(📄 알파벳순 폴더 선정·`run.env` 실사고·"진짜 블로커" 판정 기준 등) — 전부 *실제로 굴리다 깨져서 생긴 항목*이라 책이나 프롬프트 제품이 복제할 수 없다. → [[프로젝트-포트폴리오]]에 **"루프를 아는 것"이 아니라 "루프를 몇 달 돌린 이력"** 으로 서술.
- 🧠 **"누가 어느 정보를 못 보고 있는가"를 필드로**(연결점 ⑧·㉟): 📄 Beyond Byzantine(*조직의 부서 에이전트는 정직-고장/악의 이분법에 맞지 않고 제한된 합리성을 보인다*) + 📄 CoPlan의 **역할 기반 논증 그래프** + 📄 Socially Grounded Agentic AI(*복수의 정당한 관점*). 🧠 여러 이해관계자 요구를 합칠 때 **관점을 역할로 명시**하고 각 역할이 못 보는 정보를 적어두면, 세 논문이 지적한 문제를 동시에 다룬다.

## 5. 완료되면 자동으로 (요청서에 안 써도 됨)
📄 올림푸스가 알아서 하는 것들 — 요청서는 "무엇을"만, "어떻게 마무리"는 파이프라인 담당:
- 각 작업 green → 작업 브랜치에 자동 커밋
- 전체 완료 → 최종 verify → **최종 승인은 메일 답장**(승인 요청 메일에 **답장 첫 줄 `y`**, 보류 `n`) → 자동 머지 → 배포 → 기획서를 `spec/_done/`으로 아카이브 + state 초기화
- 도중 블로커/의도질문은 폰으로 옴 → **GitHub 앱**에서 `## 답변` 채워 답하면 이어감(자유서술 필요해 GitHub 유지). 최종 승인만 메일 답장으로 분리(가장 잦은 yes/no라 경량화). 상세: [[올림푸스-Olympus]] 원격 결정 브리지
- 📄 (2026-07-09 개선) **모든 발신 메일이 응답 방법을 본문 상단에 명시**한다 — 승인 메일="이 메일에 답장, 첫 줄 y/n", 질문 대기 메일="답장 반영 안 됨 → GitHub 문서 ## 답변 편집", 진행/토큰대기 알림="회신 불필요". 메일만 보고 헷갈리지 않게(`remote.sh`·`milestones.sh`·`resilience.sh`, 커밋 `8d7919b`).

## 6. 실행 (참고)
```bash
cd ~/IdeaProjects/olympus
bash reset.sh                              # 새 요청서면 state 초기화
TARGET_REPO=~/IdeaProjects/<repo> \
REMOTE=1 POLL_TIMEOUT_SEC=1800 \
VERIFY_CMD="<검증 명령>" \
  bash run.sh
```
- `REMOTE=1` = 개입을 폰으로. 끄면 터미널에서 처리.
- 배포/머지/아카이브 자동. 끄려면 `AUTO_MERGE=0` / `DEPLOY_ON_DONE=0` / `ARCHIVE_ON_DONE=0`.
- **토큰 소진 자동 대기·재개**(기본 켜짐, `TOKEN_WAIT=1`) 📄: 장시간 무인 실행 중 Claude Code **사용량 한도**에 걸려도 자동으로 리셋까지 기다렸다 그 자리에서 이어간다 → **요청서에 쓸 필요 없는 런타임 기능**(그냥 두면 됨). 끄려면 `TOKEN_WAIT=0`, 재확인 간격은 `TOKEN_RETRY_SEC`(기본 1200초). 대기 중 토큰 ≈0. 단 프로세스가 죽으면 유실 → 다시 `bash run.sh`(state에서 재개). 상세: [[올림푸스-Olympus]] §헤드리스 무인 실행.
