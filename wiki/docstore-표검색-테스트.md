> [!tip] 핵심 takeaway
> 📄 **테스터로 지원을 갔지만, 테스트 환경·도구·데이터 파이프라인·판정 자동화를 스스로 만들어 주도한 작업**이다(사용자 확인 2026-11-19). 결론은 엑셀 표를 RAG 문서 저장소(docstore)에 올릴 때 **표 위 제목·설명 한 줄이 있느냐가 검색 성공을 통째로 가른다**는 것(제목 있음 15/15, 제목 없음 0/15).
> 🧠 포트폴리오 포인트는 "버그 리포트하는 테스터"가 아니라 **측정 가능한 실험 체계를 설계하고, 결과를 고객용 문서 작성 가이드로 바꾼 사람**이라는 점. 엔진 설정보다 문서 쓰는 법이 먼저라는 결론도 직접 낸 것이다.

## 1. 문제 📄
- 사내 RAG 문서 저장소(docstore)에 고객사 상품 문서(인도네시아어·영어, 엑셀 43 + PDF·TXT 51 = 94개)를 올렸더니 **표 안 값**을 묻는 질문이 잘 안 잡혔다.
- 원인 후보가 많았다: 청크 크기, 표 복원 방식, 문서에 붙은 목차, 표 제목 유무, 표 배치. 화면에서 질문 몇 개 던져 보는 방식으로는 무엇이 원인인지 가릴 수 없었다.
- 실데이터로 테스트한 결과는 고객사에 그대로 보여 줄 수 없었다(고객 데이터 노출 문제).

## 2. 내 역할 📄
- 공식 역할은 **테스터 지원**. 그러나 테스트 방식은 직접 설계했다(사용자 확인 2026-11-19).
- 직접 만든 것:
  1. 저장소별 검색 결과를 수치로 비교하는 로컬 도구 [[rag-compare]]
  2. 테스트 문서를 검색에 맞게 재가공하는 파이프라인(규칙 SPEC + 병렬 변환 + 표 카탈로그)
  3. 변수를 통제한 가상 데이터 샘플과 생성 스크립트
  4. 복합 질문을 쪼개 저장소 4곳을 한 번에 검색하고 저장소별로 판정하는 샘플 챗봇
  5. 고객 전달용 결과 문서와 문서 작성 가이드(한국어·영어)
- 작업 방식: 방향·판단은 본인이 하고, 코드·대량 변환은 Claude Code에 시켰다(세션 기록). 🧠 판단의 예: "정답 기준은 정리본이 아니라 저장소에 올린 파일", "목차 때문에 목차 청크가 먼저 나온다", "제목 없는 표에서도 다 찾아지면 테스트가 안 된다, 더 어렵게".

## 3. 전체 구조 🧠 (자료를 종합한 그림)

```
[원본 문서 94개] ──(SPEC 규칙 + 병렬 변환)──▶ 원어 제목 청크본 (표 1개 = 청크 1개)
        │                                     └─▶ 표 카탈로그(표 473개 메타) · 검색어 · UUID 매핑
        ▼
  docstore 저장소 N개 (청크 설정 / 표 제목 유무 / 배치만 다르게)
        ▲                                   ▲
        │ /api/query 프록시                  │ docsearch 노드 4개
  [rag-compare 로컬 도구]               [샘플 챗봇: 질문 분해 → 저장소별 검색 → LLM 판정]
   - 질의 × 저장소 정답 순위·MRR           - 복합 질문을 단일 의도로 나눔
   - testset JSON 저장/불러오기            - 의도마다 4개 저장소 검색, 청크 병합
   - HTML 리포트                          - 저장소별 "찾음 / 표 구분 불가 / 청크 없음"
        ▲
  [가상 데이터 생성 스크립트] → 엑셀 4형태(제목 有/無 × 가로/세로)
```

## 4. 만든 것 상세

### 4-1. rag-compare — 저장소별 검색 비교 도구 📄
- 구성: `server.py`(145줄, Python 표준 라이브러리만) + `static/index.html`(778줄, 단일 화면). 설치 없이 `python3 server.py` → `127.0.0.1:8765`.
- 서버(`server.py`):
  - `SimpleHTTPRequestHandler` 상속 `Handler`. `GET /api/config`·`/api/testset`, `POST /api/testset`·`/api/query`.
  - `/api/query`는 docstore 검색 API로 넘기는 **프록시**. 브라우저에서 바로 부르면 CORS에 막히고 키가 노출되므로 키는 로컬 서버에만 둔다. 허용 파라미터만 전달(`input`, `storeId`, `topn`, `score`, `restore_table`), 타임아웃 120초.
  - 설정은 gitignore된 설정 파일 또는 환경변수. `argparse`로 `--port`, `--no-browser`.
- 화면(`index.html`): 저장소별 성적(정답 포함 수, 1위 정답 수, MRR, 평균 1위 점수, 정답 파일 아닌 결과 비율, 빈 셀·Unnamed 열·표 제목 없음·PII 마스킹·중복 청크·응답 시간), 문장형 분석, 질의 × 저장소 순위 표(칸 클릭 → 청크 원문 + 정답 문구 강조).
- 정답 판정: 정답 문구의 모든 줄이 든 청크를 정답으로 봄. 표 기호·공백·`1000`/`1000.0` 차이 무시.

### 4-2. 테스트 문서 재가공 파이프라인 📄
- **정리본**(10-19): 94개 파일 텍스트를 뽑아 서브에이전트 9개로 병렬 분석 → 파일별·표별 정리(표 443개, 원본 불일치 250곳 표시). 묶음 목록 마지막 줄에 개행이 없어 묶음마다 마지막 파일이 빠진 걸 발견해 재지시로 보완.
- **목차 삭제본**: 목차·설명 청크가 실제 내용보다 먼저 검색되는 문제를 보고 목차를 걷어낸 판을 따로 만듦.
- **원어 제목 청크본**(10-19): docstore가 제목마다 자른다는 점을 이용. `SPEC.md` 한 장에 규칙을 고정하고(번역 금지, 표 행 생략 금지, `##`만, `## {파일명} — {섹션 경로}`, 본문 300~1,500자, 이미지 표는 OCR 표시) 파일 94개를 `parts/NN.md`로 병렬 변환 → 합본. 이후 **표 하나 = 청크 하나** 판(`parts-table/`)으로 다시 만들어 1,649청크.
- **표 카탈로그**(10-19~20): 표 473개마다 원어+영어 제목·설명·키워드·예상 질문·샘플 행을 붙인 메타 문서. 다른 임베딩 모델이 "질문 → 어느 표"를 먼저 고르는 용도. 본문 청크와는 제목으로 연결. 검색어는 "표에 실제 있는 제목 → 없으면 설명형"으로 따로 뽑음(`doctest-표-검색어.json/tsv`).
- **UUID 실험**(10-21): 이름 없는 표 52개에 임시 UUID를 붙여 제목 대신 쓰고, 카탈로그에 매핑(원본은 `backup-before-uuid/`에 보관).

### 4-4. 샘플 챗봇 — 복합 질문 자동 판정 📄
- 사내 챗봇 빌더로 만든 "Docstore 연동 샘플" 봇(11-04 전달, 11-05 영문판).
- 흐름: 환영 → **LLM이 질문을 단일 의도로 분해**(tool call `ask_docs`) → 분해 질의 저장 → **질의마다 반복 검색** → 저장소 4곳 각각 docsearch → 결과를 LLM에 반환 → 최종 답 + **저장소별 의도별 판정**.
- 판정 형식: 의도마다 `찾음 / 실패(표 구분 불가) / 실패(청크 없음)` + 표 확인 근거(제목·설명 인용).
- 청크 병합 코드 리뷰(11-03): 여러 질의가 같은 청크를 찾으면 질의를 덧붙이는 `existing` 병합 로직이 필요한지 직접 문제 제기. 🧠 이 코드가 query를 덮어써 질의-청크가 어긋나는 문제가 남은 이슈로 기록됨.
- 프롬프트 조정 교훈(11-03): 프롬프트를 고치자 결과가 통째로 달라짐 → 이미 공유한 파일 기준으로 결과가 재현되게 프롬프트를 맞춤. "제목 없는 표에서는 찾지 못해야 정상"이라는 기대를 프롬프트에 명시.

## 7. 임팩트
- 📄 고객사에 샘플 봇 + 저장소 4개 + 결과 문서 + **문서 작성 가이드**(표마다 제목 1줄, 제목에 구분 기준, 설명 1줄에 셀에 없는 정보, 표 바로 위에 붙이기, 세로 배치, 표 사이 빈 행) 전달(11-04, 한·영).
- 🧠 "검색이 안 된다"는 막연한 문제를 **문서 쪽에서 해결 가능한 규칙**으로 바꿨다. 엔진 수정 없이 고객이 바로 적용할 수 있다.
- 🧠 질문 세트·생성 스크립트·도구가 남아 있어 다음 파서/청킹 변경 때 같은 테스트를 다시 돌릴 수 있다(회귀 테스트 자산).

## 8. 회고 / 배운 점 🧠
- 같은 헤더 표가 여럿이면 **제목이 유일한 구분 단서**다. 셀에 없는 정보(단위·기간·마감)는 설명 줄이 없으면 검색할 텍스트 자체가 없고, 그때 나온 답은 할루시네이션이다.
- 실데이터 테스트는 정답 기준이 흔들린다. **가상 데이터로 변수를 하나씩 통제**한 쪽이 결론이 훨씬 분명했다.
- 테스트가 "다 통과"하면 테스트가 약한 것이다. 질문을 계속 어렵게 바꾼 과정(10-26, 11-03 두 번)이 결과를 만들었다.
- LLM 판정은 프롬프트에 민감하다. 판정 기준을 고정하지 않으면 같은 데이터에서도 결과가 바뀐다 → 정량 판정(rag-compare)과 LLM 판정(샘플 봇)을 같이 둔 게 맞았다.
- 아쉬운 점: 초기 청크 설정 비교의 수치를 저장하지 않았다. 결과 JSON/HTML 리포트를 남기는 습관이 필요.
